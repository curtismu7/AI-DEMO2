# Privilege agent features — master index

The ten agent-facing Privilege features this demo trains on, in demo arc
order, each with a one-line description and links to the detailed docs. The
presenter-facing version of this list (with say/show lines and pre-session
checks) is the [Agent Field Guide](privilege-agent-field-guide.html).

Arc: **identity → policy → LLM surface → MCP surface → human control →
proof.**

| # | Feature | What it is | Detailed docs | How to demo — and what it proves |
|---|---|---|---|---|
| 1 | **Agent Registry** | Every agent enrolls with its own key — owner, expiry, lifecycle, per-key policy; expired keys are edit-locked until renewed | [AGENT-REGISTRY-SIDECAR-ROLLOUT](../privilege/AGENT-REGISTRY-SIDECAR-ROLLOUT.md) · [Setting up a calling agent](../privilege/GATEWAY-SETTING-UP-A-CALLING-AGENT.md) | [Rollout recipe](../privilege/AGENT-REGISTRY-SIDECAR-ROLLOUT.md) · Privilege console (`local.procyon.ai:8643` → Agent Registry). Show the 10 enrolled keys with their owners/expiries, the `/inspect` sidecar check, and the expired-key edit lock. **Proves:** agents are first-class identities with a lifecycle — not anonymous API keys. |
| 2 | **Per-credential inspection policy** | Allow / alert / sanitize / block attach to the credential or application, not the network; one credential can observe while another enforces | [AIGuard console walkthrough](../privilege/GATEWAY-AIGUARD.md) · [Guardrails & the external detector](../privilege/GATEWAY-GUARDRAILS-AND-THE-EXTERNAL-DETECTOR.md) | [Console walkthrough](../privilege/GATEWAY-AIGUARD.md) · Privilege console → key → Runtime Protection. Set one credential to alert-only and walk its events while another enforces. **Proves:** policy attaches to the credential — observe before you enforce. |
| 3 | **Virtual keys** | The app never holds a provider API key — a virtual key is useless outside the gateway; Privilege injects the real key server-side | [LLM routing & virtual keys](../privilege/GATEWAY-LLM-ROUTING-AND-VIRTUAL-KEYS.md) · [LLM protection in the demo stack](privilege-llm-protection.md) | [Demo steps](privilege-llm-protection.md) · [app: /privilege-mcp-client](https://ai-demo.ping-devops.com/privilege-mcp-client). Send a prompt and point at the gateway-route + latency line under the reply. **Proves:** the app never holds the provider key — the call visibly went through Privilege. |
| 4 | **Attributable denial** | A policy denies a call before the provider and the denial names provider, route, and the policy's own reason (`llm_policy_denied` / `llm_policy_response_denied`) | [v1.261009 demo runbook](../privilege/GATEWAY-RELEASE-v1.261009-DEMO.md) · [LLM protection](privilege-llm-protection.md) | [Demo steps](privilege-llm-protection.md) · [app: /privilege-mcp-client → Prove the policy](https://ai-demo.ping-devops.com/privilege-mcp-client). One click sends a PII prompt the active policy withholds; the panel renders provider, route, and the policy's reason. **Proves:** the denial is the feature working, and it names why. |
| 5 | **Model allowlists** | A virtual key restricted to a subset of its provider's models, enforced at the gateway as a 403 in ~40 ms — nothing leaves the gateway | [LLM routing & virtual keys](../privilege/GATEWAY-LLM-ROUTING-AND-VIRTUAL-KEYS.md) · [verified allowlist table](privilege-llm-protection.md) | [Demo steps](privilege-llm-protection.md) · [app: /llm-gateway → Chat console](https://ai-demo.ping-devops.com/llm-gateway), model dropdown. Pick a blocked model: "Privilege stopped this", "Reached the model: no", ~40 ms refusal. **Proves:** enforcement happens at the gateway — nothing left to wait for. |
| 6 | **Three routes, two wire shapes** | Anthropic native Messages API vs OpenAI-compatible for OpenAI/Google — same policy and gateway, only the wire shape changes | [LLM protection — the three routes](privilege-llm-protection.md) | [Demo steps](privilege-llm-protection.md) · [app: /llm-gateway → Chat console](https://ai-demo.ping-devops.com/llm-gateway) (three lanes) + **Raw request** tab. Send the same prompt down all three lanes; show the untouched wire on Raw request. **Proves:** one gateway, one policy, three providers — only the wire shape differs. |
| 7 | **MCP tool-call inspection** | Two enforcement surfaces: model request/response AND the MCP tool-call boundary incl. tool results; governed twin DENYs dangerous tools, ungoverned ALLOWs all, no policy = DENY ALL | [Hostile MCP side-by-side](../privilege/HOSTILE-MCP-SIDE-BY-SIDE.md) · [Red team: hostile A2A](../privilege/RED-TEAM-HOSTILE-A2A.md) | [Side-by-side runbook](../privilege/HOSTILE-MCP-SIDE-BY-SIDE.md) · twin hostile servers through their gateway doors; [app: /llm-gateway → Malicious MCP — Catalog](https://ai-demo.ping-devops.com/llm-gateway?tab=catalog) for the single-server view. Run the matrix: governed twin DENYs `create_transfer`/`delete_all_records`/`grant_admin`, ungoverned ALLOWs, no policy = DENY ALL. **Proves:** the same poison lands in both, but only the governed agent's dangerous actions die — the tool-call boundary is the enforcement point. |
| 8 | **Human-in-the-loop approvals** | Native `agentapprovals`: a high-risk agent action becomes an ApprovalReq, the human decides in the console, the grant is time-bound and auditable. Slack/Teams delivery is an open Ping case; the console path is the demo | [Agent approvals — the demo that works today](../privilege/AGENT-APPROVALS-DEMO.md) | [Demo script](../privilege/AGENT-APPROVALS-DEMO.md) · Privilege console (`local.procyon.ai:8643`) → Access Request Approvals → HITL Requests. Create an ApprovalReq, show it Awaiting, approve as the human, show the terminal state and expiry. **Proves:** the agent pauses, a human decides, the audit shows who — and the grant dies on schedule. |
| 9 | **Attack Lab** | Eight attack types against the real agent — Tool Abuse, Tool Poisoning, Schema Violation, Inter-Agent Abuse, Malicious Content — with strict verdict attribution | [AIGuard training guide](privilege-aiguard-training.md) | [Presenter table](privilege-aiguard-training.md) · [app: /llm-gateway → Attack Lab](https://ai-demo.ping-devops.com/llm-gateway?tab=attacks). Run Tool Poisoning live, then read the enforcement-component field aloud. **Proves:** the attacks are real against the real agent, and a block counts only when Privilege signs it. |
| 10 | **Audit evidence** | Every governed call leaves a Privilege event with an enforcement-component field and framework mappings (MITRE ATLAS / NIST AI RMF / OWASP LLM, catalog `aigw-compliance-v1.1.0` — verified in the gateway log 2026-10-13) | [Audit evidence & compliance mappings](../privilege/AUDIT-EVIDENCE-COMPLIANCE.md) · [Logging with Elasticsearch](../privilege/GATEWAY-LOGGING-WITH-ELASTICSEARCH.md) | [Where to show each piece](../privilege/AUDIT-EVIDENCE-COMPLIANCE.md) · [app: /llm-gateway → Attack Lab](https://ai-demo.ping-devops.com/llm-gateway?tab=attacks) to generate a fresh verdict, then the gateway pod log (grep `llm_request_blocked`) or Kibana to show it. **Proves:** every verdict names its frameworks, every denial names the policy and principal — if the audit can't show it, it didn't happen. |

## Beyond the ten — the rest of the Privilege feature surface

Features 11–21 are the other Privilege capabilities with a dedicated doc in
`privilege/`. They are not in the field guide's top-ten arc; several are
platform or admin features rather than agent-facing ones, and some are
documented-but-not-demoable (marked in the last column). Same columns as above.

| # | Feature | What it is | Detailed docs | How to demo — and what it proves |
|---|---|---|---|---|
| 11 | **MCP discovery-gating** | An MCP client's `tools/list` contains only the tools its policy grants — the agent never learns the others exist. A door with no policy is deny-by-default from the first `initialize` | [MCP-DISCOVERY-DEMO](../privilege/MCP-DISCOVERY-DEMO.md) · [Registering an MCP server](../privilege/GATEWAY-REGISTERING-AN-MCP-SERVER.md) · [Connecting an MCP client](../privilege/GATEWAY-CONNECTING-AN-MCP-CLIENT.md) | [SE demo script](../privilege/MCP-DISCOVERY-DEMO.md) · [app: /mcp-discovery](https://ai-demo.ping-devops.com/mcp-discovery) + sign in on [/privilege-mcp-client](https://ai-demo.ping-devops.com/privilege-mcp-client) against `opensearch22` (permit) then `opensearch` (deny). Keep the gateway log tailing for `Removing unauthorized tool from MCP response`. **Proves:** the backend has nine tools, the grant is a subset, and the client can't tell the rest exist — not disabled, undiscoverable. If `opensearch22` 403s, the 3-month policy box expired: renew it, don't debug. |
| 12 | **Aggregate apps** | Many MCP servers behind one address; tools are prefixed `<member>__<tool>`; the grant on the aggregate decides what's visible, each member still applies its own access and backend credential | [GATEWAY-AGGREGATE-APPS](../privilege/GATEWAY-AGGREGATE-APPS.md) | [Verifying section](../privilege/GATEWAY-AGGREGATE-APPS.md) · door `https://mcpgw.ai-demo.ping-devops.com/aggregate/mcp`. List tools, show the prefixed names, then call one granted tool. **Proves:** one address, central control of which tools an agent gets. **Caveat:** a listed tool can still fail or hang because of its member, and full sign-in through the aggregate isn't yet recorded — rehearse first. |
| 13 | **Agent-to-agent (A2A) through the gateway** | A Remote Agent app fronts an A2A agent (agent card + JSON-RPC) with the same per-app sign-in, policy, and logging as MCP; agents can chain three deep, each hop through the gateway with its own agent key | [GATEWAY-AGENT-TO-AGENT-A2A](../privilege/GATEWAY-AGENT-TO-AGENT-A2A.md) · [Ping's reference demo, explained](../privilege/PINGS-REFERENCE-DEMO-EXPLAINED.md) · [A2A demo & setup](../privilege/A2A-DEMO-AND-SETUP-OUR-ENVIRONMENT.md) | [A2A guide — Verifying](../privilege/GATEWAY-AGENT-TO-AGENT-A2A.md) · [app: /a2a-architecture](https://ai-demo.ping-devops.com/a2a-architecture). Call a remote agent via its gateway door with an agent key, then show the call in the gateway log. **Proves:** agent-to-agent traffic is governed exactly like tool traffic — the caller's gateway token is never passed on. |
| 14 | **A2A guardrails** | The gateway inspects A2A messages before the remote agent sees them; the guardrail belongs to the *calling agent's key*, so two callers can get different treatment for the same message | [GATEWAY-GUARDRAILS-FOR-A2A](../privilege/GATEWAY-GUARDRAILS-FOR-A2A.md) · [Red team: hostile A2A](../privilege/RED-TEAM-HOSTILE-A2A.md) | [Guide — What a block looks like](../privilege/GATEWAY-GUARDRAILS-FOR-A2A.md) · send a prompt injection with an agent key (blocked, 400 JSON-RPC error), then jailbreak wording (passes with an alert). **Proves:** inspection is per-credential and distinguishes block from alert. **Say honestly:** only agent-key calls are screened (a signed-in person isn't), and PII / exfil-to-outside-address passed with no record in testing. |
| 15 | **Backend auth modes (MCP + A2A)** | Per-app Auth Mode decides what the *backend* receives: None, Static Token, User Token, Pass Agent Token (OAuth: avoid on this build). The caller's own credential is never forwarded | [AUTH-MODES-MCP-BACKENDS](../privilege/AUTH-MODES-MCP-BACKENDS.md) · [A2A auth modes compared](../privilege/GATEWAY-A2A-AUTH-MODES-COMPARED.md) · [Workload identity for agent callers](../privilege/WORKLOAD-IDENTITY-AGENT-CALLERS.md) | [Comparison table](../privilege/GATEWAY-A2A-AUTH-MODES-COMPARED.md) · Privilege console → Add/Edit application → Auth Mode. Flip None → Static Token on a Remote Agent and show the agent's `Bearer authentication required` become a 200. **Proves:** the Auth Mode is the only thing that puts a credential on the last hop. **Not demoable:** Pass Agent Token needs a caller holding a workload identity — none does yet (the SPIFFE gap is written up). |
| 16 | **CIMD client documents** | Client ID Metadata Documents: an AI client's `client_id` is an https URL Privilege fetches and allow-lists — no client secret, no open self-registration | [CIMD client documents](2026-10-07-cimd-privilege-client-documents.md) | [Doc — flow & boundary](2026-10-07-cimd-privilege-client-documents.md) · [app: /cimd-privilege](https://ai-demo.ping-devops.com/cimd-privilege). Show our agents' public documents and the three-way comparison (pre-registration / DCR / CIMD). **Proves:** a client's identity can hang off a URL its owner controls. **Not yet proven:** Privilege accepting *our* documents and completing a sign-in — only Claude's public document is known to be fetched. |
| 17 | **Policy union model** | The effective grant is the union of every non-expired policy binding the identity: create adds, expiry and delete silently subtract, editing a policy down does nothing while a broader one stands | [PRIVILEGE-POLICIES-IN-DEPTH](../privilege/PRIVILEGE-POLICIES-IN-DEPTH.md) · [Lessons learned](../privilege/LESSONS-LEARNED.md) | [Four behaviors, measured](../privilege/PRIVILEGE-POLICIES-IN-DEPTH.md) · console policy list + the `[mcpfilter] cap header` log line. Create, expire, and delete a policy and watch `tools/list` change. **Proves:** why a "fix the policy" round usually adds a policy instead — the grant is a set, not a rule. The 3-tool union count is one observed instance; the mechanism is the claim. |
| 18 | **Tag policies and tags** | Tag policies are name-regex → tag-set rules that do **not** auto-tag (measured); tags actually land via the `CTags` PUT on each resource | [TAG-POLICIES](../privilege/TAG-POLICIES.md) · [Current configuration — Tag map](../privilege/CURRENT-CONFIGURATION.md) | [Doc — tag policies vs tags](../privilege/TAG-POLICIES.md) · console "Tags And Labels" panel + the live `demo-map-*` set. **Proves:** what the feature name implies and what it does are different — set the expectation before a customer builds on it. Admin feature; not an agent-facing demo. |
| 19 | **Privilege Agent (device-bound identity)** | The desktop Agent pairs one user to one workstation with identity in the Secure Enclave — an identity anchor, **not** an MCP transport; all MCP here runs through the agentless gateways | [AGENT-MODE-END-TO-END](../privilege/AGENT-MODE-END-TO-END.md) · [SE1 Agent setup (Mac)](../privilege/SE1-Privilege-Agent-Setup-Mac.md) · [Agent configuration](../privilege/AGENT-CONFIGURATION.md) *(stale-bannered)* | [Doc — pairing order](../privilege/AGENT-MODE-END-TO-END.md) · local console on the paired Mac. Show the paired device and the cloud frontend's 403 gate. **Proves:** workstation identity vs no workstation identity. Generate the new onboarding link *before* disconnecting — re-pairing erases the previous tenant's identity. |
| 20 | **Secrets Hub** | Connects Privilege to a store you already run (AWS, Google, Azure, Delinea, CyberArk beta); admins view secrets and grant named users time-limited access through a policy | [SECRETS-HUB-WITH-GOOGLE-SECRET-MANAGER](../privilege/SECRETS-HUB-WITH-GOOGLE-SECRET-MANAGER.md) | [Doc — Granting access with a policy](../privilege/SECRETS-HUB-WITH-GOOGLE-SECRET-MANAGER.md) · Privilege console → Secrets Hub. **Proves:** secret access as a time-boxed, audited grant. **Caveats to disclose:** the hub asks for Secret Manager *Admin*, sync needs the Cloud Resource Manager API too, and the pasted service-account key lands in the audit log in clear text. Not in Ping's published docs. |
| 21 | **Sensor enforcement** | The Privilege sensor finds AI workloads and, when the console says so, **terminates** denied processes — it lets them start, then kills them (including ones already running) | [SENSOR-ENFORCEMENT-POLICIES](../privilege/SENSOR-ENFORCEMENT-POLICIES.md) · [Docker guide](../privilege/SENSOR-DOCKER-GUIDE.md) · [Kubernetes guide](../privilege/SENSOR-KUBERNETES-GUIDE.md) | [Trying it safely](../privilege/SENSOR-ENFORCEMENT-POLICIES.md) · throwaway `enf-target` container + a second sensor with `-controller ""` in `-enforce audit`; read the `would_kill` counter. **Proves:** workload-level enforcement without touching the host — the console decides, not the command line. Always run audit mode first. |
