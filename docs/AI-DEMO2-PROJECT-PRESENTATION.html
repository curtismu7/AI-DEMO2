01 / Purpose

What it does

It demonstrates the controls around an agent’s access.

A user asks an AI agent to do something. The system proves who the user is, narrows what the agent may access, checks policy, and pauses for a person when needed.

Identity
PingOne sign-in, MFA, OAuth tokens, and actor identity
Control
Scopes, audiences, policy decisions, consent, and revocation
Evidence
Token chain, decision traces, audit events, and learning views

This is a demo and education platform, not a production banking service. Sample financial records are demo data; identity flows can call a configured PingOne environment.

Read data in seconds. Make a sensitive change with proof.

05 / AI runtime

AI and LLM functionality

Language chooses the action.
Identity still decides access.

1 · Deterministic route

Heuristics handle common requests and chips without an LLM round-trip. This gives known tasks a fast, predictable path.

2 · LLM intent route

For free text, a configured model returns structured intent; a tool pipeline—not the model—enforces access controls.

3 · Safe fallback

If the model is unavailable or unclear, the heuristic result remains available; guardrails run before the model path.

Providers include Ping AI / Helix, OpenAI, Anthropic Claude, LM Studio and local model services. Agent runtimes include LangChain, OpenAI Agents SDK, Mastra and Pydantic AI. The stack also has a local LLM proxy for model routing.

Model/provider availability depends on credentials, flags, local hardware and which optional services are started. A heuristic-only mode can run without an LLM key.

07 / One request

How the pieces work together

A transfer request crosses multiple independent checks.

Prompt“Move $600 to savings” is parsed into a transfer intent.
BFFChecks session, user context, feature configuration and request policy.
ExchangePingOne issues an audience-bound token with only the required scopes.
GatewayValidates token, route, scope, policy, risk and consent requirements.
ToolConsent / step-up completes; authorized tool runs and outcome is traced.

Identity context stays attached

The subject remains the user. When configured, actor/delegation claims identify the agent. The target audience and scopes constrain the downstream token.

Decision evidence comes back

Token events, gateway outcomes and audit records support the Token Chain, flow diagram, policy inspector and admin audit views.

08 / Authentication

Authentication and authorization

Tokens are server-side; the UI gets a session.

Sign-in and session

OIDC authorization code + PKCE, state/nonce checks, server-side access and refresh tokens, httpOnly session cookie, refresh and revocation.

Agent delegation

RFC 8693 exchange narrows audience and scope. Optional two-exchange flows add an actor identity. RFC 7662 introspection and JWKS/signature checks validate credentials.

Action gates

Per-tool scope checks, PingOne Authorize policies, resource ownership, intent/risk rules, and route-level public/user/admin requirements.

Human approval

HITL consent, OTP, MFA step-up, CIBA and other flows demonstrate approval or stronger authentication before selected actions proceed.

The repository distinguishes controls that are enabled by configuration from protocol demos that need a provisioned PingOne application, API grant, or external setup.

09 / Interfaces

APIs and integrations

Standards at the boundary; REST, MCP and events inside.

Identity, policy and security APIs

  • PingOne OIDC/OAuth endpoints: authorize, token, logout, introspection, revocation
  • Management API for apps, users, scopes and environment setup
  • Authorize decisions, MFA/device authentication and CIBA
  • PAR, DPoP and resource metadata in dedicated protocol flows
  • Optional PingFederate/PingGateway and PingOne Privilege demos

Agent, tool and model interfaces

  • Browser-facing Express /api/* endpoints
  • MCP tools over JSON-RPC / WebSocket and HTTP transports
  • AG-UI event stream over server-sent events
  • OpenAI-compatible model API through the local proxy
  • REST resource servers; selected OAuth-to-API-key conversion path
  • Weather/search tools and external clients such as LibreChat

The BFF is the browser-token custodian and the main application API boundary. Agent services talk to the BFF or gateway; downstream resource servers receive the protocol supported by that route.

10 / Data

Database and storage

Embedded persistence for the BFF; specialist stores for supporting services.

Primary BFF data

LMDB named databases hold local sessions, app configuration, demo banking accounts and transactions, delegations, user/demo state, audit and operational records.

Deployment-dependent state

Redis or Upstash can persist sessions in container/serverless modes. A shared persistent volume keeps local LMDB data across container replacement.

Specialist stores

SQLite, files, in-memory stores and observability backends appear where a dedicated service or demo needs them. Prometheus, Loki and Jaeger store telemetry—not application banking records.

The storage model follows the demo’s distributed shape: persistent BFF state, ephemeral runtime state where appropriate, and optional infrastructure-backed telemetry.

Do not read this as a single normalized production banking database. Data shape and persistence differ by subsystem and deployment profile.

14 / Decisions

Challenges and decisions visible in the code

Several design choices answer the same question: how can a presenter prove the control actually ran?

Keep tokens out of the browser

A BFF session boundary reduces direct token exposure and gives one place to orchestrate OAuth and downstream calls.

Separate model choice from access policy

Multiple runtimes and providers can change while gateway and token rules remain the enforcement layer.

Offer fast deterministic routes

Heuristics keep common tasks usable when models are slow or unavailable; LLM routing broadens natural-language coverage.

Put approval in the actual path

A challenge-and-retry flow makes consent and stronger authentication part of tool execution, not just a slide or mock.

Make complex behavior visible

Token-chain and decision inspectors explain trust transitions that would otherwise be hidden across services.

Configuration carries real complexity

Many identity modes require correctly provisioned apps, scopes, audiences and environment-specific URLs; setup and validation became first-class features.

These are interpretations from architecture, fixes and regression docs—not an attributed statement of original author intent.

OPEN / IN PROGRESS

Known follow-up

TECH_DEBT.md records open issues: a privilege-agent path that bypasses the common auth pipeline, duplicated agent UI code, provisioning gaps, and shared event/token-chain feeds lacking per-user filtering. Planning docs and the backlog contain more work.

How to interpret this status

“Implemented” means code and documented routes exist; it does not mean every demo mode is enabled by default, connected to a live tenant, or verified in this presentation task. The repository itself calls out limitations and known security follow-up.
