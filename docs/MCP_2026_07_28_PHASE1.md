# MCP 2026-07-28 — Phase 1 Compatibility Prep

**Branch**: `mcp-2026-phase1`  
**Status**: Complete  
**Date**: 2026-07-23

---

## Overview

The MCP specification published a Release Candidate on 2026-07-28 with breaking protocol
changes. This document records the Phase 1 (non-breaking) prep work done to bring the
banking demo MCP server toward dual-stack compliance.

Phase 1 adds new capabilities **without** removing existing ones. Existing 2025-11-25 clients
continue to work unchanged. Phase 2 (future) will introduce breaking changes
(remove session handshake, SSE, `Mcp-Session-Id`) once client migration is complete.

## RFC Compliance Assessment

### Breaking Changes in 2026-07-28

| Change | Spec Section | Phase |
|--------|-------------|-------|
| `initialize` handshake removed; replaced by `server/discover` | §lifecycle | Phase 2 |
| `Mcp-Session-Id` / stateful sessions removed; `_meta` on every request | §transport | Phase 2 |
| SSE streams (`GET /mcp`) removed; elicitation via Multi Round-Trip | §transport | Phase 2 |
| Routing headers (`Mcp-Method`, `Mcp-Name`) now mandatory | SEP-2243 | Phase 1 ✅ |

| `iss` claim validation required (RFC 9207, SEP-2468) | §auth | Phase 1 ✅ |
| OIDC `application_type` declaration | §auth | Phase 2 |

## Phase 1 Changes

### 1. Routing Headers (SEP-2243)

**Files**: `demo_mcp_server/src/server/HttpMCPTransport.ts`  
**Commit**: `2aa36d8f`

Added `Mcp-Method` and `Mcp-Name` header support to enable stateless load balancer routing
without JSON body inspection.

- `Mcp-Method`: must match the JSON-RPC `method` field (e.g., `tools/call`)
- `Mcp-Name`: for `tools/call` requests, must match `params.name`
- Headers are **optional** during the 2025-11-25 compatibility period
- If present, they are **validated** for consistency — mismatch returns `400 Invalid Request`

### 2. Cache Metadata (HTTP Cache-Control model)

**Files**: `demo_mcp_server/src/interfaces/mcp.ts`, `demo_mcp_server/src/server/MCPMessageHandler.ts`  
**Commit**: `9eec669e`

Extended `tools/list` responses with explicit caching hints:

```json
{
  "result": {
    "tools": [...],
    "ttlMs": 3600000,
    "cacheScope": "shared"
  }
}
```

- `ttlMs`: 3600000 (1 hour) — clients may cache the tools list for this duration
- `cacheScope`: `"shared"` — the tools list does not vary per user

### 3. RFC 9207 `iss` Claim Validation (Mix-up Attack Prevention)

**Files**: `demo_mcp_server/src/server/HttpMCPTransport.ts`  
**Commit**: `36915024`

Added issuer validation in `authenticateBearer()` per SEP-2468 (RFC 9207) to prevent
authorization server mix-up attacks where a token issued by a different AS is replayed.

- Only validates when the token signature was verified (`tokenInfo.signatureVerified`)
- Compares token `iss` claim against `PINGONE_ISSUER` environment variable
- Falls back to `config.authServerUrl` if `PINGONE_ISSUER` is unset
- Fail-closed: tokens with a mismatched issuer are rejected with `401`
- Logs mismatch events for audit

### 4. Protocol Version Detection & Session Tracking

**Files**: `demo_mcp_server/src/server/HttpMCPTransport.ts`, `demo_mcp_server/src/server/protocolVersions.ts`  
**Commit**: `a8e4ae35`

The `MCP-Protocol-Version` header value is now detected at session creation and stored
in the `HttpSession` object. This lays the groundwork for Phase 2 per-session routing:

```
2025-11-25 sessions → stateful handlers (current)
2026-07-28 sessions → stateless handlers (Phase 2)
```

The supported version set and latest version string are centralised in
`protocolVersions.ts` so all consumers stay in sync:

```typescript
export const MCP_LATEST_PROTOCOL_VERSION = '2026-07-28';
export const MCP_SUPPORTED_VERSIONS = ['2026-07-28', '2025-11-25', '2024-11-05'];
```

## Phase 2 Roadmap

Phase 2 introduces **breaking** protocol changes. A version-routing switch in
`handlePost` will dispatch to version-specific handler logic:

1. **`server/discover` method** — replaces `initialize` for 2026-07-28 clients; returns
   server capabilities without establishing a session
2. **Stateless `_meta` model** — client sends `clientInfo` + capabilities on every
   request instead of once during handshake; `BankingSessionManager` lookup bypassed
3. **Remove SSE (`GET /mcp`)** — `handleGet` returns `405`; elicitation moved to
   Multi Round-Trip Requests using `InputRequiredResult`
4. **Remove `Mcp-Session-Id`** — `handleDelete` becomes a no-op / `404` for
   2026-07-28 clients; session map retained for 2025-11-25 clients during migration

**Architecture decision for Phase 2**: single `handlePost` with version-aware
conditional logic (recommended for minimal diff) vs. separate handler classes per
version (cleaner long-term, higher refactor cost).
