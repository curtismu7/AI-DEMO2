## The gate the invites live behind (PR #1191, this session)

`feat/auth: public SPA root on SE + plus-addressing wall with demo allowlist`
(commit `8c68a7ec4`, merged, deployed and verified live):

1. **Public SPA root** — `k8s/aws/se-ingress.yaml` bypasses hosted-access for
   `/` (Exact match only). Deep links stay behind the wall. The invite
   wizard is reachable at `/` and `/welcome` without a login bounce.
2. **Plus-addressing wall** — `evaluateHostedIdentity` denies `+`-addressed
   aliases (`email_plus_addressed`). The sign-in modal (password + device
   forms) mirrors it inline before any flow opens, reading the new public
   `GET /api/auth/hosted-access/identifier-policy` so UI and server can't
   drift. Policy-fetch failure fails open; the server gate is the wall.
3. **Demo identifier allowlist** — `HOSTED_ACCESS_ALLOWED_IDENTIFIERS`
   (exact match on PingOne-asserted `preferred_username`/email) exempts named
   accounts from the `+` AND domain rules. Required because demoUser's real
   PingOne identity IS `cmuir+demo-user@pingone.com`, and demoAdmin is
   provisioned `@api.ping.demo` (can never pass the domain check). The group
   requirement still applies to allowlisted accounts; only PingOne can assert
   these identifiers, so an attacker-chosen value can't ride the bypass.
4. **SE configmap pin** — deploy.sh patches
   `ai-demo-config` with
   `HOSTED_ACCESS_ALLOWED_IDENTIFIERS=demoUser,demoAdmin,cmuir+demo-user@pingone.com`.

**Why this matters for invites:** invited users sign in through the same
hosted-access front door. Real Ping/PingOne employees pass on their clean
`@pingidentity.com`/`@pingone.com` email. Aliases (`cmuir+x@pingone.com`) are
refused, so invite emails should go to base addresses, not plus-tagged ones.

## How invites + gate interact (the practical bit)

- Invited user receives the password email → signs in at
  `https://ai-demo.ping-devops.com/` (public now) → hosted-access gate checks
  domain (`pingidentity.com`/`pingone.com`), plus-addressing, and group
  membership (`HOSTED_ACCESS_REQUIRED_GROUP_ID`).
- If the invited user was added to the hosted-access group in PingOne, they
  pass; otherwise `group_not_allowed` → 403 restricted page.
- Stale sessions from before a policy change fail with a dead state at
  `/callback` (403 "Access restricted"). Recovery: fresh tab / clear site
  cookies, sign in from `/`. (Known UX gap: the restricted page has no
  "start over" link yet.)

## Revoking the demo exemption later

Clear the configmap value (or drop it from deploy.sh's patch):

```bash
kubectl patch configmap ai-demo-config -n ping-devops-cmuir --context us \
  --type merge -p '{"data":{"HOSTED_ACCESS_ALLOWED_IDENTIFIERS":""}}'
```

Then only real ping-domain, non-alias, group-member accounts can sign in.
The policy fingerprint changes, invalidating all existing approvals —
everyone signs in fresh.
