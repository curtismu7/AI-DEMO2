# Vault-Backed Secrets for K8s Deployments Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make `k8s/create-secrets.sh` vault-aware so a secret's value always comes from `secrets.vault`, never from a service's `.env` file, closing the drift class that broke live PingOne auth on the SE cluster on 2026-08-25.

**Architecture:** `k8s/create-secrets.sh` gains a vault-lookup step: before pushing a key into a K8s Secret, it checks whether that key name exists in the vault (`node demo_api_server/scripts/vault.js list`); if so, its value comes from `vault.js get <name>` and any non-empty `.env` value for that same name aborts the deploy (guard-rail). Keys not in the vault keep resolving from `.env` exactly as today. The existing `demo_api_server/scripts/vault-migrate.js` — already a closed-allowlist, `demo_api_server`-scoped migration tool — is extended (allowlist only; its existing `DEMO_API_ENV_FILE` env-var override already lets it load any service's `.env`) and then run once per service to move every secret-shaped value into the vault, after which those lines are deleted from each `.env` file.

**Tech Stack:** Bash (`k8s/create-secrets.sh`), Node/CommonJS (`demo_api_server/scripts/vault-migrate.js`, `demo_api_server/scripts/vault.js`), Jest (`demo_api_server/tests/`).

**Spec:** `docs/superpowers/specs/2026-08-25-vault-in-k8s-design.md`

## Global Constraints

- No runtime code changes in `demo_mcp_gateway`, `demo_authz_server`, `oauth-mcp`, `demo_hitl_service`, `langchain_agent`, `demo_agent_service`, or `ping-gateway` — all secret delivery stays deploy-time-only, via `k8s/create-secrets.sh`.
- `.env` files carry non-secret values only once migration completes (client IDs, URLs, ports, flags); secret material lives only in the vault.
- Vault lookups fail closed: a missing/unreadable vault entry for a key `create-secrets.sh` expects there aborts the deploy rather than pushing an empty value.
- The vault-migration allowlist (`ALLOWED_ENV_VARS` in `vault-migrate.js`) stays a closed, explicitly-enumerated list — no wildcard/pattern-based sweep of `process.env` (existing security property T-269-23, must not regress).
- The guard-rail (secret-shaped key found non-empty in `.env` when the vault already has it) is a hard failure of the deploy, not a warning — matches this repo's fail-closed convention.
- Never print a secret value to stdout/stderr/logs in any new script code — mirror `vault-migrate.js`'s existing "name + length only" convention (T-269-21).

- [ ] **Step 2: Add a one-time vault-password read and vault-key-list cache near the top of the script**

Add this after the existing `derive_ns()` function and before the `# ── Re-create secrets from .env files` section (this plan assumes `create-secrets.sh` is invoked with `VAULT_PASSWORD` already exported by the caller, matching how `se-update-config.sh` already sources `demo_api_server/.env` for other values — if it isn't, this step must also read it from `demo_api_server/.env` the same way `derive_ns()` reads `PING_EMAIL`):

```bash
# ── Vault: cache the key list once so every secret_from_envfile() call can
# cheaply check "is this key vault-managed" without re-opening the vault
# per key. Fail closed: no vault, no VAULT_PASSWORD → abort, don't silently
# fall back to .env for what should be vault-only secrets.
VAULT_SCRIPT="$BASEDIR/demo_api_server/scripts/vault.js"
[ -f "$VAULT_SCRIPT" ] || die "vault script not found at $VAULT_SCRIPT"
[ -n "${VAULT_PASSWORD:-}" ] || die "VAULT_PASSWORD is required (export it or source demo_api_server/.env first)"
info "Reading vault key list..."
VAULT_KEYS="$(VAULT_PASSWORD="$VAULT_PASSWORD" node "$VAULT_SCRIPT" list)" \
  || die "vault: failed to list keys — check VAULT_PASSWORD and secrets.vault"

vault_has_key() {
  # Exact-line match against the cached newline-separated key list.
  printf '%s\n' "$VAULT_KEYS" | grep -qxF -- "$1"
}

vault_get() {
  VAULT_PASSWORD="$VAULT_PASSWORD" node "$VAULT_SCRIPT" get "$1" \
    || die "vault: failed to read $1"
}
```

- [ ] **Step 4: Change `secret_from_envfile()`'s value-resolution loop to prefer the vault**

Find this existing block inside `secret_from_envfile()` (the loop that builds `args`):

```bash
  local args=()
  for k in "${keys[@]}"; do
    local v="${!k:-}"
    [ -n "$v" ] && args+=(--from-literal="${k}=${v}")
  done
```

Replace it with:

```bash
  local args=() dry_run_report=()
  for k in "${keys[@]}"; do
    local env_v="${!k:-}"
    if vault_has_key "$k"; then
      if [ -n "$env_v" ]; then
        die "SECURITY: $k is vault-managed but $env_file also has a non-empty value for it. Vault is the only allowed source for this key — remove the $k line from $env_file. (This is exactly the drift class that broke SE introspection on 2026-08-25 — see docs/superpowers/specs/2026-08-25-vault-in-k8s-design.md.)"
      fi
      local vault_v
      vault_v="$(vault_get "$k")"
      [ -n "$vault_v" ] && args+=(--from-literal="${k}=${vault_v}")
      dry_run_report+=("$k -> vault")
    else
      [ -n "$env_v" ] && args+=(--from-literal="${k}=${env_v}")
      dry_run_report+=("$k -> .env")
    fi
  done
  if [ "${DRY_RUN:-0}" = "1" ]; then
    printf '[dry-run] %s:\n' "$secret_name"
    printf '  %s\n' "${dry_run_report[@]}"
    return
  fi
```
