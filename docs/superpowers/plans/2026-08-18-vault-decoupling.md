# Vault Decoupling & OSS-Vault Evaluation — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. **Do not start executing until the Open Decisions in §7 are ratified — the top-level scope decision (§3) is still the operator's call.**

**Goal:** Remove the cross-package coupling where `demo_agent_service`, `demo_mcp_gateway`, and `oauth-mcp` `require('../../demo_api_server/lib/vault')` at runtime and in tests — without weakening secret handling.

**Architecture:** Keep the homegrown vault as the **BFF's runtime secret store** (it uses features no env-encryptor provides), and give each of the three downstream services its **own encrypted `.env`, decrypted at startup by an OSS tool (dotenvx)** whose only job is "secrets → `process.env`". Provisioning generates each service's encrypted `.env` from the BFF vault, which stays the single source of truth.

**Tech Stack:** Node ≥ 22; existing `lib/vault` (Argon2id + AES-256-GCM + HKDF-HMAC); candidate OSS tool `@dotenvx/dotenvx` (BSD-3); jest / ts-jest / vitest; docker-compose + native `run.sh` + k8s.

**Spec:** this document is self-contained (there is no separate spec); it is grounded in the vault-ecosystem map produced 2026-08-18 (see §2) and the TECH_DEBT entry *"`demo_agent_service` tests import `demo_api_server`'s vault across the package boundary"* (2026-08-17, re-scoped 2026-08-18).

## Global Constraints

- **Do not rotate live secrets.** Re-encrypting the *storage* of an existing secret into a per-service `.env` is fine; changing the secret *value* is not. (memory: `feedback-do-not-rotate-secrets`.)
- **No secret values in git, argv, or YAML.** Encrypted `.env` files and the vault file are gitignored; passwords/keys travel via env only, never argv (existing rule T-269-27). Each loader must delete the decryption secret from `process.env` after load.
- **The BFF vault crypto/format is FROZEN** (`lib/vault/format.js` VERSION 1; `crypto.js` KDF_PARAMS). This plan does not change either.
- **§1 protected surface.** Token exchange / introspection depend on `PINGONE_MCP_GATEWAY_CLIENT_ID/SECRET` reaching the gateway and oauth-mcp identically (REGRESSION_PLAN §4). Any change must preserve that both still receive the same values.
- **Emoji allowlist** (`⚠️ ✅ ❌ 🔐 ✕ ✓ 👤 🔑 🪟 📚`) in any UI/user-facing copy.

## 1. The problem, precisely

Three sibling TypeScript services load secrets at startup via
`require('../../demo_api_server/lib/vault')` (`demo_agent_service/src/vault.ts:42`,
`demo_mcp_gateway/src/vault.ts:43`, `oauth-mcp/src/vault.ts:52`). That require
crosses a package root, so:

- Their **test suites** can only run where the sibling's `node_modules` (with native
  `argon2`) is installed — forcing two special-case installs in CI
  (`.github/workflows/ci.yml:230-231` and `:351-352`).
- Under **Docker** the sibling's `lib/` is absent (each service builds from its own
  context), so the require throws and the services fall back to their own `.env` via
  a `vaultLib===null` branch. **The cross-package path only actually resolves in
  native mode and in tests** — under Compose the downstream services never read the
  vault.
- A misplaced test (`demo_agent_service/tests/vault.test.ts`) reaches the sibling
  only to build a fixture.

## 2. Current state (condensed map, 2026-08-18)

- **`demo_api_server/lib/vault/`** — createVault/openVault handle with
  `read/set/delete/list/rotate/save/close`. Argon2id KEK → per-entry AES-256-GCM DEK
  → whole-file HKDF-HMAC, `seq` anti-rollback, NDJSON fail-closed audit log
  (`audit.js`). On-disk format `format.js` VERSION 1, magic `BNKV`.
- **One shared `secrets.vault`** at repo root, mode 600, **gitignored** (generated by
  `setupFresh` → `vault:create` + `vault:migrate-from-env`). Bind-mounted read-only
  into the **BFF only** (`docker-compose.yml:294`). **k8s does not use the vault.**
- **Five injection surfaces**, each different:
  1. **BFF** `services/vaultLoader.js` — loads **all** entries into `configStore`
     in-memory (`setRaw({persist:false})`); only `BFF_INTERNAL_SECRET` → `process.env`.
     Also `unlockVaultAtRuntime` (web unlock) and env-id reconcile.
  2-4. **agent / gateway / oauth-mcp** `src/vault.ts` — each opens the vault and
     copies its **prefix-allowlisted** entries → `process.env` (agent `AGENT_…`;
     gateway `MCP_GW_|PINGONE_|PROVIDER_|HELIX_|BFF_INTERNAL_|DEMO_`; oauth-mcp same
     minus `DEMO_`), then `close()` + `delete process.env.VAULT_PASSWORD`.
  5. **BFF web/admin** — `routes/adminVault.js` (`status`/`unlock`/`rotate`) and
     `services/helixKeyMigration.js` (a runtime **writer**: sets `HELIX_API_KEY` into
     the vault at BFF startup).
- **Secrets stored** (`scripts/vault-migrate.js:49-82`, ~25 names): PingOne client
  IDs/secrets, `HELIX_API_KEY`, `BFF_INTERNAL_SECRET`, `SESSION_SECRET`,
  `CONFIG_ENCRYPTION_KEY`, resource-server keys, `POSTHOG_API_KEY`.
- **`VAULT_PASSWORD`** — one password, per-service `.env`, never in YAML/argv, deleted
  after open.

## 3. The decision (read before executing)

**Key finding from the map: the homegrown vault does more than an env-encryptor.**
It supports runtime **rotate** and web **unlock**, an append-only **audit log**, and
a runtime **write** path (`helixKeyMigration`). dotenvx / SOPS provide only
"encrypted file → env vars"; they have no runtime write, rotate, unlock, or audit.
So a *full* replacement of `lib/vault` would be a capability **downgrade** for the
BFF, plus a re-provisioning project — not a clean win.

But the three downstream services **do not use any of those features** — they only
need "load my allowlisted secrets into `process.env` at startup." That is exactly
what dotenvx does, per-service, in every runtime mode (native, Docker, k8s, CI),
with **no cross-package require** and **no cross-build-context vendoring**.

Therefore the recommended scope is a **hybrid, not a wholesale replacement:**

| | Approach | Coupling fixed? | Risk | Capability change |
|---|---|---|---|---|
| **A (recommended)** | Keep BFF `lib/vault`; the 3 downstream services adopt **dotenvx** with their own encrypted `.env`, generated from the BFF vault at provisioning | Yes — no sibling require anywhere | Medium | None lost (services never used the runtime features) |
| B | Replace `lib/vault` entirely with dotenvx/SOPS | Yes | High | **Loses** BFF rotate/unlock/audit/write unless reimplemented |
| C | Extract `lib/vault` into a workspace package all 4 depend on | Yes in native/test | Low crypto risk, but **must vendor the package into each service's Docker build context or publish it** — the very context-isolation that makes today's require fail | None |
| D | Do nothing (status quo) | No | None | None; keeps the CI install hacks |

**Recommendation: A.** It fixes the actual coupling in every mode, deletes the CI
hacks, drops the `argon2` cross-dependency from the three services, keeps the good
BFF vault, and loses nothing. C is tempting (no crypto change) but the per-service
**Docker build contexts** mean a local shared package must be copied into each image
or published — reintroducing distribution complexity that dotenvx sidesteps. B is a
net downgrade. **Ratify A (or pick another) in §7 before executing.**

The remainder of this plan details **Approach A**. §6 sketches B/C for contrast.

## 4. Target design (Approach A)

- The **BFF vault remains the single source of truth** and is unchanged.
- **Provisioning** (`refresh-service-envs.js` / `setupFresh`) gains a step: for each
  downstream service, export that service's allowlisted secret subset from the vault
  and write it as that service's **dotenvx-encrypted `.env`** (`.env` +
  `.env.keys`), keyed by a per-service keypair. The public key ships in the image;
  the private key is provided at runtime as `DOTENV_PRIVATE_KEY` (the dotenvx analog
  of `VAULT_PASSWORD`) via the same channels `VAULT_PASSWORD` uses today (per-service
  `.env`/secret, never YAML/argv).
- Each downstream service's `src/vault.ts` is replaced by a thin
  `loadSecretsIntoEnv()` that calls dotenvx to decrypt its own `.env` and keeps the
  **existing prefix allowlist** (so only intended keys reach `process.env`) and the
  **existing fail-fast/log semantics** (missing key when secrets exist → loud;
  otherwise warn).
- **No service requires `demo_api_server/lib/vault` anymore.**

### File structure (Approach A)

- Modify: `demo_agent_service/src/vault.ts`, `demo_mcp_gateway/src/vault.ts`,
  `oauth-mcp/src/vault.ts` → dotenvx-backed loader (keep allowlist + fail semantics).
- Modify: each service's `package.json` → add `@dotenvx/dotenvx`, remove nothing that

- Delete: `demo_agent_service/tests/vault.test.ts` cross-package fixture use; replace

  `DOTENV_PRIVATE_KEY` (or mount the encrypted `.env`) to each downstream service;
  `run.sh` native path likewise; `k8s/*` if/when those services should get secrets
  there (currently they don't).
- Modify: `.github/workflows/ci.yml` → **delete** the two argon2 install steps
  (`:230-231`, `:351-352`).
- Modify: `docker-compose.yml:290-291` comment (fix the "committed" drift).

## 6. Alternatives (for the record)

- **B — full dotenvx/SOPS replacement of `lib/vault`:** also migrate the BFF. Requires
  reimplementing rotate/unlock/audit/write on top of the OSS tool (SOPS has none of
  these; HashiCorp Vault has all of them but is a server — wrong footprint for this
  demo). Larger, riskier, and only worth it if retiring the homegrown crypto is an
  explicit goal. Not recommended.
- **C — workspace package `@ai-demo/vault`:** move `lib/vault` (with its own `argon2`
  dep) into a package all four consumers depend on. Zero crypto change, keeps every
  feature. The catch: the three services build in **separate Docker contexts**, so the
  package must be vendored into each image or published to a registry — the exact
  distribution problem that makes today's sibling require fail under Docker. Viable if
  you adopt npm workspaces + a build that copies the package into each context, but
  that build plumbing is the real work. Reasonable fallback if the team prefers "no new
  dependency, no re-encryption" over dotenvx.

## 7. Open decisions to lock before executing

1. **Scope:** ratify **A** (hybrid: keep BFF vault, dotenvx the 3 services), or choose
   B / C / D. (Recommendation: A.)
2. **OSS tool for A:** `@dotenvx/dotenvx` (npm-native, keypair, `dotenvx run`/API) vs
   SOPS (`sops exec-env`, age/KMS). (Recommendation: dotenvx — matches the
   load-into-env model with the least ops surface. Verify current license +
   maintenance before adopting.)
3. **Key custody:** where does each service's `DOTENV_PRIVATE_KEY` live at runtime
   (per-service `.env` like `VAULT_PASSWORD` today), and is it distinct per service or
   shared? (Recommendation: distinct per service, same channel as `VAULT_PASSWORD`.)
4. **k8s:** the downstream services currently get **no** vault secrets under k8s. Does
   this migration change that (give them encrypted `.env` there too), or preserve
   today's behavior? (Recommendation: preserve; treat k8s secret delivery as a
   separate follow-up.)
5. **Source of truth:** confirm the BFF vault stays authoritative and provisioning
   generates the per-service encrypted `.env` from it (so there is one place secrets
   are edited).

## 8. Risks & rollback

- **Risk: a service boots without its secrets** (wrong/absent `DOTENV_PRIVATE_KEY`).
  Mitigation: keep the existing fail-fast-when-secrets-expected semantics; a native
  `run.sh`/`run-docker.sh` decrypt preflight per service (mirror the BFF's
  `vault_preflight`). Rollback: each service PR is independent and revertible; until
  all land, the vault path still works in native mode.
- **Risk: §1/§4 identity drift** (gateway vs oauth-mcp client id/secret diverge).
  Mitigation: Tasks 3-4 assert byte-identical values; add a topology check if cheap.
- **Risk: secret leakage via a tracked file.** Mitigation: `.env.keys` and decrypted
  `.env` gitignored; gitleaks pre-commit already runs; provisioning writes the private
  key to no tracked file.
- **Risk: re-provisioning is mistaken for secret rotation.** It is not — values are
  copied from the existing vault, not regenerated. Call this out in each PR.
