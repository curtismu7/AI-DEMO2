- [x] 1.3 Add a new model to an existing key's allowed list, save, capture the audit record (proves the list is live, not cached) — DONE 2026-10-12 via console API (PUT agentaccesskeys/default/openai, RevisionID 15→16, added `gpt-5.5-2026-04-23`); audit endpoint not exposed by the tenant API key (`/v1/audit` → "User is not authorized"), so the revision bump + immediate gateway effect is the change proof
- [x] 1.4 Curl through the gateway with the newly allowed model — expect the provider's normal 200 answer, capture response + `LLM request` log line. DONE 2026-10-12, two halves:
  - New catalog model already allowed: `gpt-5.6-sol` → 200 (`"content":"OK"`, usage 8+4 tokens). NOTE: this model rejects `max_tokens` — OpenAI's new-generation models require `max_completion_tokens` (provider-shaped error passed through the gateway verbatim: `"param":"max_tokens","code":"unsupported_parameter"`).
  - The model refused pre-edit became allowed post-edit: `gpt-5.5-2026-04-23` → 403 `not allowed for this key` before the PUT, 200 `"content":"OK"` after — allowlist is live, not cached.
  - Log line: `{"msg":"LLM request","Provider":"openai","Model":"gpt-5.6-sol","HTTPStatus":200,"UpstreamStatus":200,"LatencyMs":1331,"PromptTokens":8,"CompletionTokens":4,"CostUSD":0.000112,"PriceSource":"builtin"}` — **new models are priced by the builtin table the day they ship** (`PriceSource:"builtin"`, contrast with the custom lane's `unpriced`).

- [x] 1.6 Record: does pricing/budget treatment change for new models? Whether a BudgetUSD on a key whose ONLY model is unpriced ever refuses remains untested — blocked-with-reason.

## Task 2 — `llm_policy_response_denied` (demoable now)

**Narrative:** "Policy now has a distinct verdict on the *response* side. The request was fine — the model's answer tripped the rule, and the log says so by name."

This is the least-certain feature: the string exists in the binary, but how a response-side rule is authored in the console is not known. Expect discovery here.

Steps to test:

- [ ] 2.1 Discovery: find where response-side policy is authored in the console (AI policy editor — check whether rules can target responses; if not obvious, try the LLM rule editor's applies_to / direction field). Record the console path and a screenshot
- [ ] 2.2 Author a rule that matches text likely to appear only in a *response* (e.g. block a marker phrase, ask the model to say it) and attach it via the key's policy/guardrail settings
- [ ] 2.3 Curl a prompt that forces the marker into the response. Record: does the client get the answer, a redacted answer, or a denial? Status/body
- [ ] 2.4 Log check: search Kibana for `llm_policy_response_denied`. Confirm the event name, its fields, and how it differs from the request-side `llm_policy_denied` line
- [ ] 2.5 Negative control: same call without the rule — clean 200, no event. Both log lines side by side in the runbook

Deliverable: tested table rows for 2.1–2.5, or a blocked note if response-side rules cannot be authored in this console build (then the demo story is "the gateway is ready; the console UI to author it ships separately" — verify that claim before writing it).

## Task 5 — llama.cpp provider (demoable now)

**Narrative:** "Not every model lives in someone else's cloud. The gateway now fronts llama.cpp — a model running on our own hardware — with the same virtual keys, budgets, and policy as OpenAI. Full data residency, same governance."

Environment facts (set up 2026-10-12): the console's llama.cpp option saves as provider **`custom`** (OpenAI-Compatible upstream), route **`/llm/custom/v1/chat/completions`** — verified live; `/llm/llamacpp` and every other guess are NOT routable (generic OAuth challenge). Virtual key `llama.cpp` (renamed from `meta.llama3-2-3b-instruct`), allowed models `llama.cpp`, `gpt-4o-mini`, `meta.llama3-2-3b-instruct-v1:0`. The gateway forwards to the key's CustomUpstream **from inside its AWS pod**, so `127.0.0.1` upstreams 404 — the working upstream is the public ingress to the SE cluster's llm-proxy: `https://ai-demo.ping-devops.com/llm-gw` (rewrite-prefix ingress → llm-proxy:8090 → llama tier). Secured end to end: the gateway injects the key's RealKey as the upstream bearer and the cluster tier1 enforces `--api-key` (llama-server); llm-proxy forwards `LLAMA_TIER_API_KEY` for its own traffic. End-to-end verified live with the tier serving **Llama-3.2-3B-Instruct** (PVC swapped from Phi-4-mini 2026-10-12 — the 20Gi PVC was full; Phi removed, Llama-3.2 seeded, `LLAMA32 LIVE` 200 through the gateway, unauthenticated direct tier hit still 401). The demo BFF has a `custom` lane (PRIVILEGE_LLM_VIRTUAL_KEY_CUSTOM) tested live: 200, 1.3s. Budget: key has BudgetUSD=50 and calls succeed — custom providers have no per-token rate to meter.
