## Task 1 — Model catalog refresh (demoable now)

**Narrative:** "The gateway ships its own model list — new models appear on restart, no upgrade to your app. Here's Fable 5.1 and GPT-5.5 going through the gateway on the day of release."

Steps to test:

- [ ] 1.1 Console: open an existing Anthropic virtual key, screenshot the allowed-models dropdown showing the new IDs (`claude-fable-5-1` / `claude-opus-4-8` side by side with the retired ones gone)
- [ ] 1.2 Console: same for an OpenAI key (`gpt-5.5-2026-04-23` present, `gpt-4o` still there for contrast)
- [ ] 1.3 Add a new model to an existing key's allowed list, save, capture the audit record (proves the list is live, not cached)
- [ ] 1.4 Curl through the gateway with the newly allowed model — expect the provider's normal 200 answer, capture response + `LLM request` log line
- [ ] 1.5 Retired model refusal: curl a key restricted to a retired ID (e.g. set allowed models to `claude-3-opus-20240229` — if the console still offers it; if the dropdown dropped it, document that the console itself gates the list) — expect the allowed-models refusal (`model_not_allowed` or whatever the key returns), capture status/body/log
- [ ] 1.6 Record: does pricing/budget treatment change for new models? (set a BudgetUSD of a cent on a scratch key, call a new model, see whether spend is counted or the no-rate refusal fires: `llmgw: key %s has BudgetUSD set but model %q has no rate; refusing rather than spending uncounted`)

Deliverable: tested table rows for 1.1–1.6.

## Task 2 — `llm_policy_response_denied` (demoable now)

**Narrative:** "Policy now has a distinct verdict on the *response* side. The request was fine — the model's answer tripped the rule, and the log says so by name."

This is the least-certain feature: the string exists in the binary, but how a response-side rule is authored in the console is not known. Expect discovery here.

Steps to test:

- [ ] 2.1 Discovery: find where response-side policy is authored in the console (AI policy editor — check whether rules can target responses; if not obvious, try the LLM rule editor's applies_to / direction field). Record the console path and a screenshot
- [ ] 2.2 Author a rule that matches text likely to appear only in a *response* (e.g. block a marker phrase, ask the model to say it) and attach it via the key's policy/guardrail settings
- [ ] 2.3 Curl a prompt that forces the marker into the response. Record: does the client get the answer, a redacted answer, or a denial? Status/body
- [ ] 2.4 Log check: search Kibana for `llm_policy_response_denied`. Confirm the event name, its fields, and how it differs from the request-side `llm_policy_denied` line
- [ ] 2.5 Negative control: same call without the rule — clean 200, no event. Both log lines side by side in the runbook

Deliverable: tested table rows for 2.1–2.5, or a blocked note if response-side rules cannot be authored in this console build (then the demo story is "the gateway is ready; the console UI to author it ships separately" — verify that claim before writing it).

## Task 3 — Bedrock block: mantle provider + deployments route (needs provisioning)

**Narrative:** "Two new Bedrock surfaces in one demo: a second provider family, and Azure-style deployment URLs that need no code change to target the gateway."

Provisioning prelude (do once, shared by both features):

- [ ] P.1 Obtain an AWS access key with Bedrock invoke rights (whose account: Curtis's? Ping SE? — decide before starting)
- [ ] P.2 Console: Virtual Keys → new key, provider **bedrock-mantle** (check the dropdown: is mantle offered directly? if only `bedrock-runtime` appears, record that mantle routing is URL-driven, not key-driven)
- [ ] P.3 Save the key, capture the audit record with the provider value
- [ ] P.4 Sanity call on the classic route `/llm/bedrock/...` with the new key to prove the credential works before blaming the new routes

Feature 3 steps (mantle):

- [ ] 3.1 Curl `/llm/bedrock-mantle/v1/messages` (or whatever path shape mantle takes — try both Anthropic and OpenAI body shapes; record which the route accepts) — capture status/body
- [ ] 3.2 Verify the `X-Procyon-Bedrock-Region` header behaviour on mantle (does it route per-region like runtime?)
- [ ] 3.3 Wrong-provider control: same key on `/llm/openai/` — expect `wrong_provider`, capture it
- [ ] 3.4 Log line for a mantle call — capture and compare with a runtime call's line

Feature 4 steps (deployments route):

- [ ] 4.1 Curl `/llm/bedrock-runtime/openai/deployments/<model>/...` with an OpenAI chat-completions body — capture status/body
- [ ] 4.2 Same call to the classic Anthropic-shaped route — confirm both return equivalent answers (the "no code change" claim, tested)
- [ ] 4.3 Log lines for both shapes — confirm they classify as the same upstream call
- [ ] 4.4 Negative: deployments route with a model not in allowed list — expect the standard refusal

Deliverable: tested table rows P.1–4.4, or blocked-with-reason on P.1 if no Bedrock key is obtainable this cycle (then 3/4 ship as "provisioned demo pending" in the runbook).
