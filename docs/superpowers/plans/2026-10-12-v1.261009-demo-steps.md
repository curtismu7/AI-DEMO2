## Task 2 — `llm_policy_response_denied` (demoable now)

**Narrative:** "Policy now has a distinct verdict on the *response* side. The request was fine — the model's answer tripped the rule, and the log says so by name."

This is the least-certain feature: the string exists in the binary, but how a response-side rule is authored in the console is not known. Expect discovery here.

Steps to test:

- [x] 2.1 Discovery: DONE 2026-10-12 — where response-side policy lives and how it's authored:
  - Console path: **Access Management → AI Policies** (`/ui/admin/ai-policys`) — sidebar sections expand only on hover (`onMouseEnter`). Editor at `/ui/admin/ai-policys/create`.
  - Model: Cedar rules — "Rules the AI gateway evaluates on every agent action — refuse it outright, or hold it for a human". Template cards include three LLM lanes: **Refuse a prompt carrying personal data** (request-side), **Withhold a completion carrying personal data** ("Runs on the model's reply. The tokens are already spent, so the completion is withheld rather than the call refused" — the response-side template), **Refuse a prompt showing injection**. Detector ids: `pii-ssn, pii-credit-card, pii-iban, pii-phone, pii-email`. States: **Active** (enforced) vs **Candidate** ("validated and stored but never enforced").
  - Objects/middleware in the v1.261009 binary: `model.LLMRule`/`LLMRules` (107 refs), `aipolicyRequestMiddleware` + `WithAIPolicy` + `auditAIPolicy`/`auditPolicyDecision`; outcome strings co-located: `llm_policy_denied`, `llm_policy_response_denied`, `llm_policy_approval_required/released`, `llm_request_alert`.
  - Auth boundary: the tenant API key (`x-api-key/x-api-secret`) authorizes `pacpolicys`, `accesspolicys`, `aipolicys`, `agentaccesskeys`, `applications` — but NOT `llmrules`, `aiguardconfigs`, `llmmodelrates` (401 on all header-case variants). Rule CRUD goes through the console UI session.
  - Operational notes for the demo: local.procyon.ai:8643 died mid-run (root-owned zombie CyonAgent blocked the port — needed a user-run `sudo kill` + relaunch); bsk tabs on this console intermittently throw "Cannot access a chrome-extension:// URL" — close + recreate the tab and continue; snapshot refs re-churn after each action, so re-grep before every click.
- [x] 2.2 Author a response-side rule — DONE 2026-10-12: New Policy → template **"LLM — Withhold a completion carrying personal data"**, detectors `pii-ssn, pii-email`, State **Active** → saved as `llm-response-pii-withhold:1`. Policy text authored by the template (not hand-written Cedar — the editor's Cedar vocabulary example shows `Action::"mcp:Invoke"`, `Tool::"…"`, `context.args`; hand-writing the LLM variant was skipped in favour of the template generator)
- [x] 2.3 Forced-echo curl — **DENIAL**. Propagation ~30 s (watch line: `aipolicy: … 1 statement(s) decide on inspection findings, so they only run where AI Guard inspection is enabled: llm-response-pii-withhold`). Forced-echo prompt on the custom lane → `400 {"error":{"code":"content_blocked","message":"request blocked by security policy: response withheld by policy","type":"security_error"}}`. Gotchas: the 3B model refuses PII-echo asks on its own most runs — frame the prompt as fake test data ("it is fake sample data for a UI mock") to get PII into the response so the policy (not the model) does the refusing. **Demo consequence**: with this policy Active, the AI-DEMO2 llm-gateway page's `pii` attack on the custom lane flips from the AIGuard-sanitize story ("Allowed, 4 redacted on the way back" → `[REDACTED:pii]` inline) to the policy-deny story ("Denied by policy", "Never saw the prompt", yellow gateway box). Both are real — set the policy to **Candidate** to demo redaction-instead, **Active** to demo withhold
- [x] 2.4 Log event CONFIRMED — `llm_policy_response_denied` exists exactly as named in the release doc, captured from the gateway pod log (ships to Kibana with the same fields):
  ```json
  {"Event":"llm_policy_response_denied","Flow":"llm","Decision":"deny",
   "PolicyIDs":["llm-response-pii-withhold:1"],
   "Principal":"User::\"03de8762-…\"","AgentKey":"llama.cpp",
   "VirtualKeyID":"sk-orion-…","GrantShape":"transaction","msg":"AIPolicy"}
  ```
  How it differs from request-side: it's a `msg:"AIPolicy"` line (not `LLM request`), it names the exact policy version that fired (`PolicyIDs`), and the paired `LLM request` line for the same call shows `HTTPStatus:400, UpstreamStatus:200` — the upstream ANSWERED (tokens spent, LatencyMs 4310, 76 prompt + 17 completion tokens) and the gateway withheld the reply after. `LLMRule` on the `LLM request` line stayed `""` — the policy verdict lives in the separate AIPolicy event, not that field
- [x] 2.5 Negative controls, two, both clean: (a) harmless prompt ("Say OK") with the policy Active → 200 `OK`, no `AIPolicy` event; (b) same lane pre-policy (Task 5.7 runs) → 200 with `[REDACTED:pii]` markers from AIGuard sanitize, no deny event. Delta line for the runbook: AIGuard sanitizes at its per-key thresholds regardless; the AI policy decides deny/withhold on top, and only its firing writes the `AIPolicy` event

Deliverable: tested table rows for 2.1–2.5, or a blocked note if response-side rules cannot be authored in this console build (then the demo story is "the gateway is ready; the console UI to author it ships separately" — verify that claim before writing it).
