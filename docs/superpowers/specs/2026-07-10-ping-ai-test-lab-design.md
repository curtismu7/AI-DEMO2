# Ping AI Test Lab — design spec

Date: 2026-07-10
Status: approved by user (interactive Q&A, 3 rounds)

## Purpose

Two deliverables:

1. **A new demo page** (`/ping-ai-test-lab`) in `demo_api_ui` + BFF endpoints in
   `demo_api_server` that exercise Ping's AI surface — the six Ping Agent
   Skills, the MCP servers reachable from the BFF, the LangChain agent chain —
   and a **CIAM evals runner** that executes deterministic PingOne checks from
   the ping-bench CIAM eval set.
2. **A Google Doc** following the "SE Help: AI-First Headless CIAM Evals"
   template: all 56 remaining CIAM rows filled in (technical success criteria
   for PingOne and AIC, one shared LLM-as-judge rubric per row, per the
   CIAM-GS-005 worked example), with live pass/fail results recorded next to
   every PingOne check that was executed against the demo environment.

## Source documents

- https://developer.pingidentity.com/build-with-ai/agent-skills/overview.html
  — six Agent Skills (ping-quickstart, ping-foundation, ping-orchestration,
  ping-universal-services, ping-app-integration, ping-identity-for-ai); the
  plugin also registers AIC MCP and DaVinci MCP servers.
- `SE Help: AI-First Headless CIAM Evals` (user-supplied MD): two-layer
  grading — deterministic technical gate first, LLM-judge rubric second
  (weights sum to 1.0). 57 rows across Getting Started / Integrate / Customize
  / Deploy / Monitor; GS-005 is the worked example.

## Page: four suites

The page follows the `/pingcli` pattern: server-side allow-listed catalog,
client sends only keys, results rendered in-page. No user-supplied input is
ever executed.

### Suite 1 — Agent Skills catalog + static checks
- Static catalog of the six Ping Agent Skills (name, purpose, install command).
- Connectivity checks, each pass/fail + latency:
  hosted PingOne MCP (`tools/list` via `mcpPingOneHttpAdapter`), demo MCP
  server (`:8080`), MCP gateway, LangChain agent health, PingOne Management
  API reachability (worker token).
- AIC MCP / DaVinci MCP appear as `not_configured` (no tenant, zero repo
  footprint) — reported, never failed.

### Suite 2 — MCP live tests
- Hosted PingOne MCP: `tools/list` + one safe read-only `tools/call`
  (reuse `mcpPingOneHttpAdapter` exactly as `routes/mcpInspector.js` does).
- Demo MCP server via the BFF executor with the RFC 8693 token-exchange chain;
  token chain steps captured in the result detail.
- MCP gateway call via `mcpGatewayClient`.

### Suite 3 — Agent-skill scenarios (LLM)
- Six prompts, one per Agent Skill domain, sent to the LangChain agent.
- BFF collects the AG-UI SSE stream server-side into a final text
  (non-streaming wrapper over the `proxyAgentSse` path) and grades each
  response with a keyword/rubric heuristic → pass/fail + excerpt.

### Suite 4 — CIAM evals runner (PingOne)
- Declarative check engine: each CIAM row's PingOne checks are data
  (`{checkId, verifies, method, path, condition}`), executed as **read-only**
  Management API GETs with the existing worker token.
- **Safety policy: live execution is read-only.** Checks that would mutate the
  environment (e2e registration, promotions, SIEM wiring) are authored in the
  doc but carry `kind: "manual"` in the engine and report status `not_run`.
- AIC checks are authored in the doc only; the runner reports AIC as
  `not_configured`.
- Row statuses: `pass` / `fail` / `not_run` (manual) / `not_configured` (AIC,
  missing feature) — a failing check never aborts the run.

## Backend

- New `demo_api_server/routes/pingAiTestLab.js`, mounted
  `app.use('/api/admin/ping-ai-test-lab', authenticateToken, ...)` (same guard
  as pingcli).
- Endpoints: `GET /suites` (catalog incl. eval rows), `POST /run {testKey}`
  (single test result JSON), `GET /run-all?suite=<key>` (SSE progressive
  results), `GET /results/latest` (last run, for export).
- Eval definitions in `demo_api_server/data/ciamEvalChecks.js` (declarative,
  PingOne checks only; doc-only content lives with the report generator, not
  the app).
- Per-test errors captured as `{status:'fail'|'error', error, detail}`.

## Frontend

- `demo_api_ui/src/components/PingAiTestLabPage.js` + `.css`; route in App.js
  mirroring the pingcli block; nav entry in the MCP group of AdminSideNav.
- Suite sections with Run buttons, result rows (✅/❌/⚠️ + latency),
  expandable `JsonHighlight` detail, copy-results-JSON affordance.
- REGRESSION_PLAN §0 respected: allowed emoji only, minimal diff to App.js /
  AdminSideNav.jsx.

## Google Doc report

- Generated by me (Claude session) from (a) authored criteria for all 56 rows
  and (b) the live run's results JSON.
- Structure mirrors the template exactly: per row — PingOne criteria table,
  AIC criteria table, shared rubric table; plus a **Live result** column/annotation
  on PingOne checks (✅ pass / ❌ fail / not run / not configured) and a run
  metadata header (env, date, stack version).
- Delivered via Google Drive connector as a Google Doc (HTML→Doc conversion).

## Testing

- Jest route test: catalog shape, unknown-key rejection, mocked adapters for
  one test per suite, eval engine condition evaluation.
- UI build gate (`demo_api_ui` build) before calling the work done.
- Live verify: run all four suites against the running Docker stack.

## Out of scope

- AIC / DaVinci MCP integration (no tenant, net-new).
- Mutating PingOne checks (registration e2e, env promotion) — authored, not
  executed.
- ping-bench YAML/schema translation (doc states engineers translate later).
