# Tool-Authz-Chain Drift Hardening — Design

**Date:** 2026-07-05
**Status:** Approved design (pending spec review)

## Goal

Make it impossible to onboard (or rename/remove) a gateway-surface MCP tool
without every downstream authorization layer staying consistent — enforced at
commit time, so the multi-layer "Unknown tool" / `SCOPE_MISMATCH` failures that
surfaced during the code-search rollout can never recur silently.

## Background

A gateway-surface tool call passes through four config layers. Onboarding
`code_search` required editing all four; three had no (or one-directional)
drift guard, so the breakage only appeared at live e2e:

| Layer | Source of truth | Guard before this work |
|---|---|---|
| Mock gateway `toolScopes` | derived from `scope-topology.json` | ✅ `scopeTopology.regression` |
| PingGateway `mcp-tool-schemas.json` | generated by `demo_mcp_gateway gen:tool-schemas` from the tool registry | ❌ drift test exists but is **not gated** |
| BFF `intentTokenService` permitted_tools | hand-curated (`INTENT_TO_PERMITTED_TOOLS` + `READ_ONLY_TOOLS`) | ⚠️ **one-directional** (listed tools must exist in SoT; new tool silently missing is undetected) |
| BFF `configStore` `buildAllowedScopesByAudience()` | hand-maintained RFC 8707 allowlist | ❌ no drift guard vs the tools that exchange through it |

The repo already has a precedent for keeping a derived artifact in lock-step:
`.husky/pre-commit` auto-regenerates the P1AZ snapshot and runs `topology:verify`
when `scope-topology.json` (and a few sibling files) are staged. This design
extends that same mechanism to the tool-authz chain.

## Non-goals (YAGNI)

- Not removing the mock gateway (kept for teaching; decision recorded).
- Not re-deriving `permitted_tools` from the SSOT (it is deliberately curated —
  intent→tool mapping is product knowledge). We guard *coverage*, not authorship.
- No product-behavior changes: invariants #2/#3 are pure derivations from
  `scope-topology.json` + the tool registry; they add tests + gate wiring only.
- Not touching the mock gateway `toolScopes` path (already SSOT-derived + gated).

## Design revision (2026-07-05, from implementation findings)

Measuring against the live tool set changed two of the three invariants:

- **Inv-2 DROPPED.** Only 42 of 204 gateway-surface tools appear in the curated
  `permitted_tools` map; the other 163 (mostly generated vertical tools + demo
  tools) are intentionally absent. "Every gateway tool must be permittable" is
  therefore false — the map is deliberately sparse (per-intent, primary tools
  only). No workable coverage invariant exists without a new "agent-reachable"
  signal, which is out of scope. The existing forward parity guard stays.
- **Inv-3 becomes fix-then-gate.** The audience allowlist is missing SIX scopes
  that gateway tools already require: `invest:read`, `permits:read`,
  `transcript:read`, `workorders:read`, `sensitive:read` (all six audiences), and
  `transfer` (mcpserver only — mcpgateway already has it). These are latent
  `SCOPE_MISMATCH` bugs for the investment / government / university / workforce /
  sensitive tools through PingGateway (the same failure `code:search` hit). So
  Inv-3 first FIXES the allowlist, then gates it.

Net scope: **Inv-1 (schema drift gate) + Inv-3 (fix 6 scopes, then gate coverage).**

## The invariants (each a gated test)

### Inv-1: PingGateway schema is regenerated
`mcp-tool-schemas.json` must byte-equal a fresh `gen:tool-schemas` run.
Already implemented as `demo_mcp_gateway/tests/toolSchemaDrift.test.ts` — this
design only **gates** it (below).

### Inv-2: every gateway-surface tool is permittable (reverse intent parity)
For every tool `t` with `surface: "gateway"` in `scope-topology.json`:
`t ∈ ( ⋃ values(INTENT_TO_PERMITTED_TOOLS) ) ∪ READ_ONLY_TOOLS`.
A tool absent from every permitted-tools list can never pass the intent-token
prompt-injection guard, so this is a hard requirement. Implemented by extending
`demo_api_server/src/__tests__/intentTokenService.scopeTopologyParity.test.js`
with the reverse direction (it currently asserts only the forward direction).

### Inv-3: the scope-audience allowlist covers every tool scope
For every gateway-surface tool `t` and every scope `s ∈ t.requiredScopes`
(normalized through `aliases{}`):
`s ∈ buildAllowedScopesByAudience()[mcpGatewayUri]` **and**
`s ∈ buildAllowedScopesByAudience()[mcpServerUri]`.
This is the precise invariant — NOT "allowlist ⊇ all mirroredScopes" (the
allowlist is intentionally a curated subset). It is exactly the check that would
have caught the `code:search` `SCOPE_MISMATCH`. New test file
`demo_api_server/src/__tests__/allowedScopesByAudience.parity.test.js`.

## Gate wiring ("always")

### `scripts/topology-verify.sh` — add three steps
Renumber to N/8 (or keep N/5 label style; align with existing). Add:
- **Inv-1:** `( cd demo_mcp_gateway && npx --no-install jest toolSchemaDrift --no-coverage --forceExit ) || fail=1`
- **Inv-2 / Inv-3:** run the two `demo_api_server` jest parity tests via the same
  `npx --no-install jest --runTestsByPath ... --testPathIgnorePatterns='/node_modules/'`
  pattern already used for `scopeTopology.regression` (step 2).

`topology:verify` runs every step (no fail-fast) so one commit shows all drift.

### `.husky/pre-commit` — extend the trigger + auto-regen
- Extend the `TOPO_TOUCHED` match to also fire when any of these are staged:
  `demo_mcp_server/src/tools/**`, `demo_mcp_resource_server/src/tools/investTools.ts`,
  `demo_mcp_gateway/src/gatewayTools.ts`,
  `demo_api_server/services/intentTokenService.js`,
  `demo_api_server/services/configStore.js`, `mcp-tool-schemas.json`.
- When triggered, **auto-regenerate `mcp-tool-schemas.json`** (mirroring the P1AZ
  auto-regen): `npm --prefix demo_mcp_gateway run --silent gen:tool-schemas` then
  `git add mcp-tool-schemas.json`. Then run `topology:verify` (which now includes
  Inv-1/2/3). Keep the existing P1AZ-snapshot regen branch intact.

## Data flow (a developer adds a tool)

1. Dev adds a tool to `BankingToolRegistry` + `scope-topology.json` (`tools` +
   any new scope). `git commit`.
2. Pre-commit sees a tool source staged → regenerates `mcp-tool-schemas.json`,
   stages it → runs `topology:verify`.
3. `topology:verify` runs Inv-1 (schema now regenerated ✓), Inv-2 (fails if the
   tool isn't permittable — message: add it to `INTENT_TO_PERMITTED_TOOLS`/
   `READ_ONLY_TOOLS`), Inv-3 (fails if a required scope isn't in the audience
   allowlist — message: add it to `buildAllowedScopesByAudience`).
4. Commit succeeds only when all four layers agree.

## Error handling / messages

Each failing invariant must print the exact remediation (tool/scope name + the
file + list to edit), matching the existing `topology:verify` failure ergonomics
("Fix the drift, or regenerate … then re-commit"). The pre-commit auto-regen is
best-effort: if `gen:tool-schemas` fails (e.g. TS error), surface it and abort
the commit rather than committing a stale schema.

## Testing

- **Inv-1:** existing `toolSchemaDrift.test.ts` (2 cases) — now also run by the gate.
- **Inv-2:** extend the existing parity test; add a negative proof (a fake
  gateway tool absent from the maps fails).
- **Inv-3:** new parity test with a positive case (all current tool scopes
  covered) and a negative proof (a tool requiring an uncovered scope fails).
- **Gate:** `npm run topology:verify` passes clean on `main` after wiring, and a
  deliberately-stale fixture (drop a tool from `mcp-tool-schemas.json`) makes it
  fail — verified manually during implementation, not committed.

## Rollout / phases (for the plan)

1. Inv-2: extend intent parity test (reverse direction) + confirm it passes for
   the current tool set.
2. Inv-3: new configStore audience-coverage parity test.
3. Gate wiring: add Inv-1/2/3 steps to `topology-verify.sh`; confirm
   `topology:verify` green.
4. Pre-commit: extend `TOPO_TOUCHED` trigger + `mcp-tool-schemas.json` auto-regen;
   confirm a tool-source commit triggers regen + the full gate.
