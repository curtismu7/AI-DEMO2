# Protecting on PingFederate identity in Privilege AI policies (Cedar)

2026-10-20. Read-only investigation of the demo tenant (`0428ba4f-…`, "AI Agent") and the SE gateway
(`mcpgw.ai-demo.ping-devops.com`, door `opensearch-hitl`). **Nothing was changed on the console.**
This guide separates what was measured from what is a design guess, because the answer to "can a PF token
claim drive a Cedar rule?" is narrower than the question assumes.

## The short answer

- **The claim gate is not Cedar.** Privilege can trust an external issuer such as PingFederate natively
  (workload identity: exact `Issuer`, mandatory `Audience`, `JwksURI`, `RequiredClaims`), and a rule in
  `pacpolicys` can require claim values on the **presented token** (`PolicyRule.RequiredClaims`). Found in the
  console swagger and walked in the console screens on 2026-10-20; **no PF identity exists and nothing has been
  exercised or saved**.
- **Cedar then decides per tool.** It reads a fixed attribute set the gateway builds (below): no
  `context.claims`, no raw `groups` claim, no hook for `act` or ID-JAG that we could find in the editor.
- **This path is for agent callers** presenting a PF-issued JWT. A person signing in through the door still gets a
  token from the Privilege-owned PingOne environment, and PF is not in that path.
- **PF scopes reaching `context.token.scopes` is untested.** Do not promise it.
- **PingFederate is not registered anywhere in Privilege today.** The tenant's IdP list is empty, the 4 existing
  Non-Human Identities are sensor identities (Kubernetes/Docker issuers), and 0 of 28 access rules use
  `RequiredClaims`.

## Native external-issuer trust (swagger, 2026-10-20; unexercised)

| Object | What it holds |
|---|---|
| `AgentWorkloadIdentity` | `Issuer` (matched exactly against `iss`), `Audience` (mandatory), `JwksURI` (preferred) or a pinned `JWKS`, `MaxTokenLifetimeSec` (0 = gateway default 3600), `RequiredClaims` (must be present, exact match), `Platform` (UI hint only: kubernetes, github_actions, spiffe, oidc) |
| `AgentAccessKey.WorkloadIdentity` | Replaces the virtual key as that key's authentication; exactly one of the two applies |
| `NonHumanIdentity` (`/v1/nonhumanidentities`) | `Federation` (the above), `Enabled` (the only kill switch), `Scopes`, `SubjectBinding`, `UserClaim` (dotted path of the claim naming the end user, default `sub`), `NotAfter` |
| `PolicyRule.RequiredClaims` (in `pacpolicys`) | Narrows a rule to callers presenting particular token claims. Any listed value of one claim matches; all listed claims must match. Empty means unconditional. Matched against the presented token, never the identity |

Pinned per identity at authentication: issuer, subject and audience. `RequiredClaims` on the rule is for what
varies from token to token. Key `Scopes` are coarse (`llm`, `mcp`, `a2a`), not Cedar-style strings.

### In the console (walked 2026-10-20, nothing saved)

**Admin → Non-Human Identities → Register Identity** (`/ui/admin/non-human-identities/create`). Four identities
already exist (`docker-cmuir`, `k8-orbstack`, and two EKS sensor identities), all for the shadow-AI sensors,
with scopes `shadowai:write policy:read llm mcp a2a`, so this federation pattern works on this tenant today.

| Form field | What it does |
|---|---|
| Token issuer type | Kubernetes, Docker Host, GitHub Actions, SPIFFE/SPIRE JWT-SVID, **OIDC Provider** ("Any OIDC provider works: GitLab CI, AWS IRSA, Azure workload identity"). Display only, never used for verification |
| Issuer (`iss`) | "Decode one of your tokens and copy its iss claim exactly" |
| Subject (`sub`) | Matched exactly against `sub` (a pattern needs an explicit "any matching workload" acknowledgement or a pinned required claim) |
| Verification keys | Fetch from a JWKS URL, or paste keys; or both (URL plus a pinned fallback) |
| Permissions | `shadowai:write`, `policy:read`, `llm`, `mcp`, `a2a`; at least one |
| End user in a presented token | **None** (the identity is the only principal), **Resolved** (look the end user up in Privilege), **Opaque** (record the end user, never look them up). Names the claim that carries the user (`UserClaim`, default `sub`) |
| Audience | **Generated by Privilege and shown after saving.** The PF token must carry exactly that `aud` |

The form code (not exercised) also has required-claim rows, a token-lifetime cap and an expiry under Advanced.

**Where the claim gate is set.** In the access policy editor for the app: "Reach each peer agent only when the
caller's verified token carries these claims. Any one listed value matches a claim; every claim must match.
Leave empty to allow unconditionally." A claim name may be a **path into the token**, such as
`realm_access.roles`, and `${aud}` stands for the identity's audience. For MCP apps, "a conditioned tier grants
only what is selected below: it never falls back to all tools", so a claim-conditioned tier is a per-tool gate.
Rules carrying claims show as "scope-gated" or "partly scope-gated" in the app's policy summary.

**Why End user matters for Cedar.** With **Resolved**, the person named in the token becomes a Privilege user,
and then `principal in Group::"x"` and per-user rules apply to them. A PF claim can therefore reach Cedar by
naming the user, not by being readable in Cedar.

## What the door trusts today (measured)

| Fact | Evidence |
|---|---|
| The door advertises **itself** as the authorization server | `/.well-known/oauth-authorization-server` issuer = `…/opensearch-hitl`; protected-resource metadata lists only that issuer |
| A client can register through the door | `POST …/opensearch-hitl/register` → 201 |
| `/authorize` redirects to PingOne environment `0428ba4f` | client `1a403855…`, scopes `openid profile email offline_access p1:read:env p1:read:user p1:read:application`, `state` = `idp\|<nonce>` |
| That environment federates onward to the demo environment | `0428ba4f` → `rp/authenticate?providerId=…` → `01d89b06` (client "Demo AI App - Privilege Tenant Federation") → sign-on (`CURRENT-CONFIGURATION.md`, "Which PingOne identity is which") |
| Privilege has **no external IdP registered** | `GET /v1/idproviders` → empty list |
| The tenant's own OIDC server has no signing keys exposed | `GET /v1/oidcservers` → one server `oidc`, empty key fields |

So the token Cedar sees is **issued by `0428ba4f`**, after a sign-in that happened in `01d89b06`. A PF
token never reaches the door; at best PF is a sign-in source behind `01d89b06`.

## What Cedar can see (measured: console editor + 5 live AI policies)

| To protect on | Cedar expression | Source |
|---|---|---|
| Token scope | `context.token.scopes.contains("x")` | template "Restrict a tool to tokens carrying a scope"; fails closed with no token |
| Agent-key scope | `context.agent.scopes.contains("x")` | editor condition `agent_scope` |
| Group of the caller | `principal in Group::"x"` | template "…for one team"; groups come from Privilege's directory |
| One named agent | `principal == Agent::"x"` | template "A named agent may never call a tool" |
| Door / app | `context.app == "x"` | every live policy |
| Tool | `resource == Tool::"x"` | every live policy |
| Tool arguments | `context.args.<name>` | templates (amount, country, …) |
| Approval state | `context has approval_count && context.approval_count >= 1` | the HITL policies |
| Content findings | `context.aiguard.pii_kinds`, `context.aiguard.categories` | PII / injection templates |

Actions: `mcp:Invoke` (refuse) and `mcp:InvokeUnattended` (hold for a human); `llm:Receive` for LLM replies.

**Not found:** `context.claims`, `principal.<attribute>`, a raw `groups` claim, `act`, ID-JAG. Absence from
the editor is not proof the engine rejects them; it is proof there is no supported way to write them.

## How a PF user becomes a Cedar principal (inferred, one measured line)

The gateway log reports its Cedar registry: `125 entities: 4 users (+4 email aliases), 4 agents, 1 groups,
112 resources`. Callers are therefore matched to **Privilege users, by email alias**, and their groups come
from the Privilege directory. *Inference:* a PF user whose email matches a Privilege user is that principal.
*Not tested.* The log never prints scopes, so scope contents could not be confirmed from logs.

## Directions

**0. For an agent holding a PF-issued JWT (route C, native, not done; writes, ask first).** Register a
Non-Human Identity of type **OIDC Provider** (or set `WorkloadIdentity` on an agent key): `Issuer` = the PF issuer
exactly as in its `iss`, `Subject` = the agent's `sub`, JWKS URL = PF's JWKS, scope `mcp`, End user = Resolved
if a claim names the person. Privilege then shows the generated `Audience`; configure PF (access token manager
audience) to mint that value. Then add `RequiredClaims` to the
`pacpolicys` rule that grants the app (for example a `groups` or `scope` value PF puts in the token). Cedar rules
(step 3) then decide per tool. The gateway logs `workload token accepted … issuer=… subject=…` or `rejected:
<reason>` (see `WORKLOAD-IDENTITY-AGENT-CALLERS.md`). **Unknown:** whether the door honours this on the MCP
path, and what `context.token.scopes` / `context.agent.scopes` hold for such a caller.

**1. Get PF into the sign-in chain (for people; not done; a write, ask first).**
- *Route A, recommended:* add PF as an external OIDC IdP in `01d89b06` (the AIC pattern, `ai-demo2-aic-external-idp`:
  IdP object + sign-on policy assigned to the federation app). Result: PF identity in, PingOne-issued token out.
- *Route B, untested:* register PF as a Privilege `IDProvider` (`ProviderType`, `OidcProvider{ProviderURL,
  ClientID, ClientSecret}` per the console swagger). Whether the gateway then trusts PF-issued tokens is unproven.

**2. Make the PF user a Privilege principal.** Ensure a Privilege user exists with the PF user's email, and
put them in the group the rule will name.

**3. Author the rule** (Access Management → AI Policies, `/ui/admin/ai-policys`). Group-gated hold, adapted
from the live `hitl-opensearch` policy (adaptation, not yet run):

```
@grant("capability")
@ttl("900")
@request_ttl("3600")
@approvers("<approver-id>")
@reason("Only the search-admins group may run SearchIndexTool without a hold")
forbid (principal, action == Action::"mcp:InvokeUnattended", resource == Tool::"SearchIndexTool")
when   { context.app == "opensearch-hitl" && !(principal in Group::"search-admins") }
unless { context has approval_count && context.approval_count >= 1 };
```

Scope-gated refusal, verbatim from the console template:

```
@reason("SearchIndexTool requires the search:read scope")
forbid (principal, action == Action::"mcp:Invoke", resource == Tool::"SearchIndexTool")
when   { context.app == "opensearch-hitl" }
unless { context.token.scopes.contains("search:read") };
```

**4. Enforce it.** Create as **Candidate** (validated, never enforced), then move to **Active**. A policy created
through the API lands with `State:''` and is never enforced until `PUT` to `Active`. AI policies live in
`aipolicys`, not `pacpolicys`. Watch the gateway log for `aipolicy: … compiled N policies`.

**5. Test through the door.** Register a client (DCR), sign in, call the tool. A refusal logs
`mcp_policy_denied`; a hold logs `mcp_policy_approval_required` and opens an approval that someone approves
under Access Request Approvals before the client retries. See `AGENT-APPROVALS-DEMO.md`.
