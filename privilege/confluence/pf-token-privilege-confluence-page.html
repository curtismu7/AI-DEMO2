Federated agents: a PingFederate token on PingOne Privilege

Written for: SEs setting this up on their own tenant. Measured: 2026-10-26 and 2026-10-27 on gateway privilege-aigw v1.261024 and v1.261027. "Federated Agents" is the coming name for what the console calls Non-Human Identities today; this page uses the console's current labels.

What this shows

An AI agent whose identity already lives in the customer's own identity provider (here PingFederate) presents the token PingFederate issued to it to a Privilege MCP server. Privilege trusts that issuer, pins the agent, decides which tools it may use, and passes the agent's own token through to the MCP server. The agent holds no Privilege secret.

The customer story: "We already register our agents in PingFederate. Govern what they can do on our MCP servers, without giving each agent a second credential."

What Privilege does here, and what it can't

Does (all measured)

WhatHow
Trusts PingFederate as the agent's issuerThe identity checks the signature (PingFederate JWKS), iss, aud (bound to one P1 Privilege Agent App) and token lifetime. Anything else: 401.
Accepts only this agentRequired claims on the identity (act.sub, client_id) must match exactly, or 401.
Holds no secret for the agentThe PingFederate token is the only credential.
Decides which tools, per agent appThe agent key's grant lists tools per agent app. No rule for the app: 403.
Gives different tools by scope (tiers)Two grant rules for the same app, each with RequiredClaims on scope: the token's scope picks 3 tools, 9 tools, or 403.
Blocks one tool by scope (Cedar)An AI policy reads context.token.scopes: SearchIndexTool is denied unless the scope has opensearch:search; other tools still work.
Passes the agent's token throughPass Agent Token forwards the PingFederate token unchanged, so the MCP server verifies it too and can read its claims.

Can't (yet)

WhatWhy, and what to use instead
Token exchange (on behalf of a user)Privilege does not exchange tokens. A token with the user in sub and the agent in act has to come from PingFederate. Privilege's OBO support is in staging (Ping, 2026-10-23).
Narrow the token it forwardsThe MCP server gets the same token the agent sent, with every scope in it.
Cedar on other token claimsCedar reads scopes but not act.sub or client_id (context.token.claims is due in a later release). Use the identity's required claims or the grant rule's RequiredClaims.
Wildcard audiencesThe audience must name the gateway. An allow-list is possible on request.
New grant policies through the APIA POSTed grant is deleted within about a minute (cause unknown). Edit the key's existing grant.

Before you start

  1. Gateway privilege-aigw v1.261024 or later (earlier versions cannot discover tools on a Pass Agent Token agent app).
  2. The agent app's backend resolves from every gateway pod (a Service name that was deleted gave "no such host"; a network policy can also block some pods).
  3. Access to PingFederate (admin console or API) and the Privilege console.

Values in angle brackets are yours; ours are in square brackets.

A. PingFederate: make the agent's token

  1. Client with the client_credentials grant. [pf-route-c-test]
  2. Scopes: add the scopes your tiers and policies use to the authorization server's scope list. [opensearch:admin, opensearch:read, opensearch:search, whoami:read]
  3. JWT access token manager for this agent (clone an existing JWT one; unique Key ID). Audience claim and Resource URIs = the agent app URL [https://mcpgw.ai-demo.ping-devops.com/pftoken/mcp]. Scope Claim Name scope. Do not add scope to the attribute contract: the manager then writes the granted scopes itself.
  4. Access token mapping (CLIENT_CREDENTIALS context): sub and client_id from Context: ClientId; act from Expression #{"sub": "<agent id>"}. act must be an object; the text "{}" fails.
  5. Make this manager the client's default access token manager.
  6. Every token request sends resource=<agent app URL>. Without it, a request that names a scope is served by a different token manager (audience enduser.ping.demo, no sub, no act) and the gateway answers 401.
  7. Check: decode a token: iss, sub, aud = the agent app URL, client_id, act.sub = the agent id, and scope as requested.

B. Privilege: register the federated agent (Non-Human Identity)

Console: Non-Human Identities → Register Identity.

  1. Token issuer type: OIDC Provider. Issuer: exactly the token's iss. [https://cmuir-pf.ping-devops.com]
  2. Key source: Fetch from URL; JWKS URL = PingFederate's. [https://cmuir-pf.ping-devops.com/pf/JWKS]
  3. Subject: *. (The agent is pinned by the required claims below.)
  4. End user in a presented token: Opaque, claim empty (= sub).
  5. Audience: the agent app URL, the same value PingFederate puts in aud.
  6. Required claims: act.sub = <agent id> and client_id = <client id>. [both pf-route-c-test]
  7. Permissions: mcp.
If the console refuses with "Spec.UserClaim resolves to sub", the subject is pinned while End user reads sub: set Subject to *.

C. Privilege: the P1 Privilege Agent App

Console: Agentic Apps → Add Application → MCP Server.

  1. MCP Server URL: a backend that resolves from every gateway pod, ending in exactly /mcp. The gateway uses the URL's path as the app's entry path: a URL saved as …/mc gave 404 and the log line outside entry path "/mc".
  2. Auth Mode: Pass Agent Token. Mesh cluster: the one your gateway pods serve.
  3. Save. The Overview shows "Awaiting first agent call".

D. Privilege: the agent key and its tools

Console: Agent Registry → Add Agent.

  1. Custodian: the identity from part B. Scope mcp. [key pftoken-agent, custodian PFtoken]
  2. Gateway & Apps: select the agent app from part C.
  3. Configure Tool Access: MCP Server = the agent app; Access tier Everyone; select the tools (none selected grants every tool).
  4. Save. The agent app's Agent Registry tab now lists the key and its grant.
Do not create the grant as a separate policy through the API: every such policy was deleted by the gateway within seconds. Edit the key's own grant instead. Keys and grants expire (ours: 2026-10-29); renew them before a demo.

E. First call and test

  1. Make one agent call with the PingFederate token (tools/list). Even if refused, it triggers tool discovery.
  2. Call again: expect 200 with the tool list. A garbage bearer still gets 401.
  3. Gateway log (all gateway pods, --all-containers): workload token accepted for key <key>, no policy denied.

F. Optional: tools by scope (tiers)

Each rule in the key's grant can require token claims (RequiredClaims). Two rules for the same app make two tiers.

  1. Read the key's grant (GET /api/<tenant>/v1/pacpolicys, the policy whose rules name your key). Save a backup.
  2. In Spec.ActionMap.MCP.PolicyRule, replace the app's rule with two copies, each with its own tools and condition:
"Capabilities": { "Map": { "tools": { "Elems": ["ListIndexTool","SearchIndexTool","CountTool"] } } },
"RequiredClaims": { "Map": { "scope": { "Elems": ["opensearch:read"] } } }

and the same with all nine tools and "Elems": ["opensearch:admin"]. PUT /api/<tenant>/v1/pacpolicys/default/<grant name> with the whole policy; it takes effect in about 20 seconds.

Token scopeResult for the same agent and agent app
openid opensearch:admin200, all 9 tools
openid opensearch:read200, 3 tools
neither403, no tools

Rules: a value list means any of; each scope in the token is matched on its own (requiring opensearch:read matches openid opensearch:read; requiring the whole string does not); claim paths may be dotted (act.sub). The value must be a list: a plain string is a 400. To remove a condition, delete the RequiredClaims field; a PUT with {"Map": {}} is ignored and the old condition stays.

G. Optional: prove the token is passed through

Create a second agent app (Pass Agent Token) in front of an MCP server that verifies the token itself and can report what it received. Ours, pftoken-rs, fronts a demo MCP server whose whoami tool returns every claim it verified. That server trusts the PingFederate issuer and JWKS and accepts the token's audience. Add a rule for the second app (tool whoami) to the key's grant, then call whoami: the issuer, act, scopes and the other claims it reports are the PingFederate token's. The gateway checked the token and passed it through; it did not swap in its own credential.

H. Commands

curl -s https://<pf-host>/as/token.oauth2 -u "<client id>:$CLIENT_SECRET" \
  -d grant_type=client_credentials \
  -d "scope=openid opensearch:read" \
  -d "resource=https://<gateway-host>/<agent app>/mcp"

curl -s https://<gateway-host>/<agent app>/mcp \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -H 'Accept: application/json, text/event-stream' \
  -d '{"jsonrpc":"2.0","id":1,"method":"tools/list"}'

I. Optional: block one tool by scope with Cedar

The grant decides which tools the agent may see; an AI policy (Cedar) can then refuse a single call based on the token. Console: AI Policies → New Policy (or POST /api/<tenant>/v1/aipolicys).

@reason("SearchIndexTool needs the opensearch:search scope in the agent's token")
forbid (principal, action == Action::"mcp:Invoke", resource == Tool::"SearchIndexTool")
when   { context.app == "pftoken" }
unless { context has token && context.token.scopes.contains("opensearch:search") };
Make it Active. A policy created through the API starts as a Candidate (State: ""): it is compiled and logged but never enforced. The gateway log then says candidate policy would have returned deny where the active set returned allow. In the console, click Enforce on the policy (or set State to Active through the API). It takes effect within seconds.
Token scopeSearchIndexToolOther tools

Gateway log for the block: aipolicy: denied PFtoken calling SearchIndexTool on pftoken. Cedar sees only the token's scopes; for other claims use the identity's required claims or the grant's RequiredClaims.
