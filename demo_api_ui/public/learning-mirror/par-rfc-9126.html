What is PAR

Pushed Authorization Requests (PAR) — RFC 9126 — flip the normal OAuth authorization-code flow so the request parameters are sent directly from the server to the authorization server before the browser redirect happens.

In a classic flow the browser carries all parameters in the URL:

GET /as/authorize ?client_id=myapp &response_type=code &scope=openid read &code_challenge=… &state=…

With PAR, the client first POSTs these to a dedicated server-side endpoint:

POST /as/par Content-Type: application/x-www-form-urlencoded Authorization: Basic <client credentials> client_id=myapp&response_type=code&scope=openid read &code_challenge=…&state=…

The AS returns a request_uri — a short-lived opaque reference:

HTTP/1.1 201 Created { "request_uri": "urn:ietf:params:oauth:request_uri:6esc_11ACC5bwc014ltc14eY", "expires_in": 90 }

The browser only ever sees the tiny reference — not the full parameter set:

GET /as/authorize ?client_id=myapp &request_uri=urn:ietf:params:oauth:request_uri:6esc_11ACC5bwc014ltc14eY

Security benefits

Why PAR matters

Risk mitigatedHow PAR helps
Parameter tamperingRequest is registered server-to-server before the browser sees it — the browser can't modify parameters.
Long URLs leaking in logsBrowser URL bar and server logs only show the opaque request_uri, not scopes, PKCE, state, etc.
Mix-up / phishing attacksClient authenticates to the PAR endpoint; AS verifies the client_id before the redirect ever happens.
Open redirect abuseAS can validate redirect_uri at push time, not just at callback — stricter window.
Replay attacksrequest_uri is one-time-use and short-lived (typically 60–90 seconds).

PAR is recommended for high-security deployments (banking, healthcare, government) and is required when using Pushed Authorization Requests + JARM or combining with DPoP (RFC 9449) for sender-constrained tokens.

Full flow

PAR + PKCE end-to-end sequence

  1. Client generates code_verifier + code_challenge (PKCE).
  2. Client POSTs all parameters to POST /as/par, authenticating with its credentials (client_secret_basic or private_key_jwt).
  3. AS validates the client, stores the request, returns request_uri.
  4. Browser is redirected to GET /as/authorize?client_id=…&request_uri=… only.
  5. User authenticates at PingOne.
  6. AS redirects back with code.
  7. Backend exchanges code + code_verifier for tokens at POST /as/token.

Steps 1–3 are invisible to the browser; the URL bar only ever shows the 60-characterrequest_uri reference.

PingOne setup

Enabling PAR in PingOne

  1. In the PingOne admin console, open your Application → OAuth settings.
  2. Enable "Pushed Authorization Requests (PAR)" under Advanced settings. PingOne exposes the PAR endpoint at:POST https://auth.pingone.com/{envId}/as/par
  3. Optionally set Require PAR to reject direct authorize requests (no request_uri → 400).
  4. Update your BFF to call /as/par before building the redirect URL. Use the returned request_uri as the sole query parameter alongsideclient_id.

The PAR endpoint URL is advertised in the AS metadata discovery document at/.well-known/openid-configuration under the keypushed_authorization_request_endpoint.

PAR vs RAR

PAR and RAR solve different problems and are frequently confused, because RAR details are normally sent inside a PAR request. The short version: PAR is about how the request travels; RAR is about what the request means.

AspectPARRAR
OAuth standardRFC 9126RFC 9396
Main purposeSecurely transport the authorization requestDescribe precisely what access or action is requested
FocusRequest delivery and integrityAuthorization detail and precision
Key parameterrequest_uriauthorization_details
Replaces scopes?NoNo — complements them with structured context
Authorizes the API call?NoNo — the AS evaluates, the resource server enforces

Used together

The client POSTs the whole request — including authorization_details — to the PAR endpoint, gets back a short-lived request_uri, and the browser carries only that reference. The user then sees a consent screen describing the specific operation (“initiate a $123.50 payment to Merchant A”) rather than a broad scope name.

Neither replaces resource-server enforcement. PAR protects how the grant was established; RAR describes what was granted. The resource server still has to validate the token and check that the operation it was handed is covered by the grant — if the client later submits $1,000 to a different merchant, only the resource server stops it.

Ping platform support

  • PingOne SSO — supports PAR (POST /{envID}/as/par, 60-second request URI, single use). It does not document native RFC 9396 processing, so PingOne SSO should not be positioned as providing native RAR.
  • PingOne Authorize — makes fine-grained policy decisions, which is not the same thing as OAuth RAR support.
  • AIC / PingAM — partial RAR support on /authorize and /par, with Remote Consent configuration.
  • PingFederate — RAR via configured authorization-detail types and processors; custom processing may be required.
