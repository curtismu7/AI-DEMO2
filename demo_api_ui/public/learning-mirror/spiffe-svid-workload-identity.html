What & Why

An SVID is an ID card for software, not for people

SVID stands for SPIFFE Verifiable Identity Document. SPIFFE (Secure Production Identity Framework For Everyone) is a CNCF standard for giving a running workload — a process, a container, an AI agent — a cryptographically verifiable identity, with no shared secret anywhere.

Two things, often confused

        SPIFFE ID  —  the name
        spiffe://bxfinance.demo/agent
                    |
        wrapped and cryptographically signed
                    |
        SVID  —  the document that proves it
        (an X.509 certificate, or a JWT)

The SPIFFE ID is a URI: a trust domain plus a path. It is the workload's name, the way an email address is a person's name. The SVID is the signed credential that proves the workload owns that name.

Two formats

FormatWhat it isUsed for
X.509-SVIDA short-lived TLS certificate carrying the SPIFFE ID in the SANmTLS between services — both sides present one and verify the other
JWT-SVIDA short-lived signed JWT whose sub is the SPIFFE IDLayer-7 HTTP/REST calls, API gateway authorization, bearer/actor tokens

How a workload gets one — attestation, not passwords

This is the part that makes SPIFFE different. The issuer never asks the workload "what is your secret?" — it looks at what the process actually is.

  1. Attestation. The workload starts and calls a local Workload API (typically a Unix domain socket — no credentials needed to call it). The issuing engine, usually SPIRE, inspects the caller: process UID, container image, Kubernetes namespace and service account, cloud instance metadata, binary hash.
  2. Issuance. If the runtime evidence matches a registration entry, the engine returns an SVID valid for a very short window — commonly 5 minutes.
  3. Usage. The workload presents the SVID to open an mTLS connection or to call an API.
  4. Auto-rotation. A background daemon or sidecar silently renews the SVID in memory before it expires. The workload never handles, stores, or rotates a raw secret.

Against the thing it replaces

 Static API key / client secretSVID
LifespanMonths to yearsMinutes, auto-rotating
StorageHardcoded, or in a .env file / secrets managerProcess memory, fetched from a local API socket
Blast radius if leakedHigh — full access until someone notices and revokesLow — the credential expires in minutes
ProvenanceAnyone holding the string can impersonate the workloadBound to the specific running binary and host by attestation
AuditabilityBlurry — who used the shared key?Clear delegation chains for agent-to-agent calls

Why this matters specifically for AI agents

  • Exfiltration. If an agent is prompt-injected or its memory is compromised, a leaked static key grants indefinite access. A leaked SVID is dead in minutes.
  • Ephemerality. Sub-agents spawn to solve one task and exit. Issuing each a permanent credential creates credential bloat nobody ever cleans up.
  • Delegation audit. When agent A calls agent B, the audit trail needs proof of who called what — not the agents' self-reported labels.

In this repo

What is real here, and what is not

P1 parity mode uses a local mock issuer

Illustrative — demo_api_server/routes/spiffeDemo.js exposes POST /api/demo/spiffe/svid, /jwks, and /verify over plain HTTP with the mock issuer spire-demo://demo.local. It issues only for a registered mock workload whose supplied selectors match. Cryptographic verification is real: the verifier checks the RS256 signature, issuer, expiry, key, and SPIFFE trust domain. Workload attestation is not real: no runtime evidence proves which process, container, pod, or node made the request. This route is not a SPIRE Workload API.

Local actor-token exchange models PingFederate behavior

This repo: demo_authz_server/routes/token.js The flag-gated local RFC 8693 path verifies the JWT-SVID against the mock issuer's published key and binds its spiffe:// subject into act.sub. This models PingFederate behavior for teaching and testing; it is not a PingOne Cloud exchange.

What is genuinely implemented

This repo: demo_api_server/services/clientAssertionService.js private_key_jwt (RFC 7521 / 7523) client authentication — the BFF signs a 60-second assertion with a private key instead of sending a client secret. The same pattern runs in agent_token_service/src/pingoneAgentToken.ts ("Mode B PKI") and demo_agent_service/src/agentIdentity.ts. This is the existing seam an SVID-sourced key would plug into. Gated by ff_token_auth_private_key_jwt.

// clientAssertionService.buildClientAssertion() — what PingOne accepts today
{
  "iss": "<pingone client_id>",   // must equal the client_id
  "sub": "<pingone client_id>",   // must equal the client_id
  "aud": "<token endpoint>",
  "exp": now + 60
}
// header: { alg: "RS256", kid }
//
// A SPIFFE ID could ride along as an extra claim — but PingOne would
// ignore it. The client_id is what authenticates.

mTLS: one hop, built, deliberately off

This repo: oauth-mcp/src/auth/mtlsMiddleware.ts The gateway-to-MCP-server hop can run mutual TLS, pinning the gateway certificate by SHA-256. MCP_MTLS_ON is the single master switch and is currently empty (off) because the Privilege MCP console-configured backend breaks against an mTLS listener — see privilege/PRIVILEGE-MCP.md. Certificates come from scripts/ensure-gateway-mtls-certs.sh, not from any attestation authority.

Proof-of-possession: DPoP, not certificate binding

This repo: demo_mcp_gateway/src/dpopVerify.ts The only sender-constraining mechanism built here is DPoP (RFC 9449), which binds a token to a key via the cnf.jkt thumbprint. Signer is demo_api_server/services/dpopKeyService.js. RFC 8705 certificate-bound access tokens (cnf with x5t#S256) are not implemented anywhere in this repo — docs/RFC-STANDARDS.md states so explicitly.

What is missing for real SPIFFE

  • No runtime workload registration or attestation; P1 matches supplied mock selectors.
  • No X.509-SVID mTLS on service hops owned by this project.

Live PingFederate integration (real SPIRE)

This repo: spiffe/README.md The opt-in spiffe Docker profile runs SPIRE 1.15.2 (server, agent,spiffe-helper, OIDC Discovery Provider) with trust domainbxfinance.demo. The discovery provider terminates the mkcert TLS pair onhttps://local.ping-devops.com:8443/keys, and PingFederate's JWT Token Processor 2.0 validates SPIRE-signed JWT-SVIDs as the RFC 8693 actor_token: the workload identity (spiffe://bxfinance.demo/bff) rides into the issued token as the spiffeId claim. See spiffe/pingfederate/ for the PF admin API artifacts.

What PingOne can consume

PingOne is a closed trust domain

The natural ambition is to hand a SPIRE-issued SVID straight to PingOne. Most of that is not possible today, and the reasons are worth knowing before designing around them. PingOne Cloud cannot consume a SPIRE SVID as an external actor token.

CapabilityPingOneWhy it matters
private_key_jwt with a registered jwksUrlSupportedThe one real opening. Point the app's jwksUrl at SPIRE's OIDC Discovery Provider and sign with an SVID-issued key. Constraint: RS256/384/512 only, and the assertion's iss and sub must both equal the PingOne client_id.
SPIRE-issued JWT as subject_token / actor_tokenNot supportedPingOne validates that the issuer of both exchange tokens matches the issuer of the current PingOne environment. There is no trusted-external-issuer object in the authorization server, so a JWT-SVID can never become the actor in an RFC 8693 exchange.
RFC 8705 mTLS client authenticationNot supportedFour token-endpoint auth methods exist and none is mTLS, so an X.509-SVID cannot authenticate the client directly.
Certificate-bound tokens (cnf / x5t#S256)Not supportedAbsent from the environment's discovery document. Combined with no DPoP support, every PingOne access token in the chain is a bearer token.
act claim on the issued tokenSupported, not automaticRequires a custom resource attribute named act driven by a PingOne Expression Language expression, plus a matching may_act claim on the subject token.
SPIFFE / SPIRE integrationPingFederate onlyPingFederate's JWT Token Processor 2.0 can trust the SPIRE OIDC Discovery Provider as an issuer, accept the JWT-SVID as an actor token, and land the full spiffe:// URI in act.sub. The equivalent PingOne guidance uses client secrets and does not mention SPIFFE.

What that leaves

One genuine win is available on PingOne cloud: delete a static client secret. Register the workload's PingOne application with private_key_jwt and a jwksUrl pointing at SPIRE, and have the workload sign its client assertion with a SPIRE-issued, auto-rotating key. Nothing long-lived stays on disk.

The SPIFFE ID itself survives only as a decorative claim — PingOne authenticates the client_id, not the workload identity. Getting a spiffe:// URI into a real act chain requires PingFederate.

One practical trap worth recording: SPIRE commonly defaults to EC P-256 keys, and PingOne accepts RS256/384/512 only. SPIRE must be configured to mint RSA-2048 or the client assertion is rejected.
