Coarse vs fine

Two enforcement points, two jobs

This demo has two authorization layers on every agent tool call: the Agent Gateway (a PEP — Policy Enforcement Point, either PingOne Agent Gateway/IG or the Node demo gateway) and PingOne Authorize (P1AZ, the PDP — Policy Decision Point). They are deliberately split by grain, not duplicated:

QuestionWho decides
Is the token real, live, mine? (authentication)Gateway
Coarse access — scope, audience, anti-bypassGateway locally and the PDP (see below)
Business policy — amount, tier, group, step-up, HITLPingOne Authorize (P1AZ)
The gateway does not re-implement P1AZ's business rules. Five checks do land on the gateway, because they need the raw token claims and call parameters the PEP holds — set membership over scopes, groups and payees, epoch-second timestamps, the full multi-valued aud. The PDP gets scalars; the PEP has the originals, so it owns those five. That's what this page covers.

Why the gateway owns it

5 checks the PEP owns

The cloud policy is a snapshot import, and its DSL compares attribute to attribute: scalars, string types, no set membership. The BFF and gateway flatten what they can into scalars for the PDP — UserTier, InRequiredGroup, TokenKidKnown. These five keep their original shape (sets, arrays, epoch numbers), so the PEP is where they get checked:

Per-tool scope membership

Per-tool scope membership (mock Rule 3): TokenScopes is a space-separated set and the DSL has no set/contains operator; enumerating scope x tool combinations as OR-of-equals would not survive multi-scope tokens.

RAR payee allow-list

RAR payee allow-list (mock Rule 3c payee half): permitted payees are an array; same missing set-membership operator.

D-05 multi-aud anti-bypass

D-05 multi-aud: TokenAudTargetsUpstream compares a SINGLE aud string; a space-joined multi-aud value is only caught at the PEP (gateway) and mock.

On the IG groovy path, P1AZ owns the RAR decision: the filter forwards RarAuthorizationDetails, RarMaxAmount and RarPermittedPayees, and the cloud RarMaxAmount rule decides — which is why ping-gateway/scripts/check-groovy-params.sh warns against a local DENY there ("P1AZ decides"). A local payee DENY is available behind PG_LOCAL_RAR_PAYEE_ENFORCE for the belt-and-braces variant. Separately, ff_rar itself is opt-in because PingOne SaaS accepts authorization_details on PAR only, so the BFF carries the grant in the TraT azd envelope; it is minted natively on AIC / PingFederate 11.2+.

Key files

  • snapshots/gen-authorize-snapshot.js — the reconciler that keeps the cloud P1AZ snapshot in sync with scope-topology.json; its header comment is the authoritative list of what's deliberately not modeled in the cloud policy.
  • demo_mcp_gateway/src/auth/GatewayTokenPolicy.ts — Node gateway's D-05 anti-bypass check, unconditional on every inbound token.
