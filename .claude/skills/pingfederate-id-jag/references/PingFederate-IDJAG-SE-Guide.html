ID-JAG on PingFederate: SE guide (Postman-led demo)

What you get: a working ID-JAG (Identity Assertion JWT Authorization Grant) demo on one PingFederate, driven from Postman. PingFederate plays three roles at once: the identity provider, the enterprise IdP that mints the ID-JAG, and the resource authorization server that redeems it.

Time: roughly 20 minutes to set up (most of it is the first PF start and the license click-through), then a 10 to 15 minute demo.

2. The idea in 60 seconds (so you can explain it)

  • A user is signed in at the company IdP. An AI agent or app now needs to call another system's API for that user.
  • Normally that means another login prompt, or a long-lived credential passed around.
  • With ID-JAG the app asks the IdP for a short-lived, signed pass that names the user, the app and the target resource server. The app hands the pass to the resource server's authorization server, which checks the IdP's signature and issues its own access token. No second login, and the IdP stays in control of who can reach what.

The flow you will demo:

 User --login--> [PF as IdP] --tokens--> App (Postman)
                                           |
        ID token / refresh / access token  |  token exchange
                                           v
                              [PF as enterprise IdP]  --ID-JAG-->  App
                                           (policy: which apps, which resource servers)
                                                                    |
                                                          JWT bearer grant
                                                                    v
                              [PF as resource authorization server] --access token--> App --> API

In this demo one PF instance is all three boxes. In production the resource authorization server is a separate system.

3. Prerequisites

  • PingFederate 13.1 or newer. ID-JAG issuance does not exist in older versions. (Tested on 13.1.4.)
  • A PingFederate license file and a Java runtime supported by your PingFederate version (see the PingFederate release notes; set JAVA_HOME).
  • Postman (desktop app).
  • Claude Code (recommended for the setup step). Without it, you can run the setup collection in Postman's Collection Runner (see 5B).
  • Node/newman is not required.

4. Step 1: get a PingFederate running

Skip to Step 2 if you already have a PF 13.1+ with the OAuth role enabled that you can freely change. Do not use a PF that other people rely on: the setup replaces its default authentication policy (it is backed up, and the teardown restores it, but use a lab PF).

  1. Unzip PingFederate 13.1.x, copy your license to pingfederate/server/default/conf/pingfederate.lic.
  2. Start it: pingfederate/bin/run.sh (Windows: run.bat). Wait for PingFederate running....
  3. Open https://localhost:9999/pingfederate/app (accept the self-signed certificate warning).
  4. Sign in as Administrator / 2Federate. Accept the license agreement and set a new admin password when prompted. Finish the first-run prompts.
  5. Check two server settings in the admin console (under System > Server): the Base URL must be https://<your host>:9031 (it becomes the ID-JAG issuer, and it is the runtime URL used throughout), and the OAuth 2.0 Authorization Server role must be enabled. You do not have to hunt for these: the setup's first step (0b, "Server settings") reads both and fails with a clear message if either is wrong.

Until step 4 is done, the admin API answers license_agreement_not_accepted.

You now know four values you'll need:

5. Step 2: build the ID-JAG setup on your PF

5A. With Claude Code (recommended)

  1. Open Claude Code in the folder that holds PingFederate-IDJAG-Setup.postman_collection.json (see "Where the files go" above).
  2. Paste this into Claude Code (fill in the placeholders):
Use the Postman collection PingFederate-IDJAG-Setup.postman_collection.json in this folder to set up ID-JAG on my PingFederate. Admin console: https://<host>:9999, admin user <user> / <password>, runtime https://<host>:9031. Read the collection description first, run the folders in order, ask me before the authentication-policy step, and finish by running the Verify folder and showing me the results.
  1. Claude will run the folders in order, and will stop and ask before folder 9 (see the warning below). Say yes on a lab PF.
  2. It finishes by running folder 10 (Verify). Success = every Verify step passes and you see ID-JAGs with typ: oauth-id-jag+jwt.

5B. Without Claude Code (Postman only)

  1. Import the Setup collection. Settings > General: turn off SSL certificate verification.
  2. On the collection's Variables tab set pf_admin, admin_user, admin_pass, pf_runtime. Leave everything else.
  3. Use the Collection Runner and run the folders in order: 0. Preflight, 1, 2, 3, 4, 5, 6, 7, 8, then 9 (only after reading the warning), then 10.
  4. Skip 0-optional unless step 0c reports no valid RSA signing key.
  5. Every request has tests that fail with PingFederate's own error message, so a problem is easy to read in the Runner results. Fix it, then rerun from that request.

What the setup creates (all names start with idjag)

Scopes; a test user (tarun / Test1234!) with a validator; a login page (HTML Form) and authentication policy contract; two access token managers (one for the user side, one for the resource-AS side); the OIDC policy that produces ID tokens; three token processors (refresh, access, ID token); the token exchange processor policy; the OAuth Token Exchange SP connection (ID-JAG enabled); the IdP connection with the OAuth assertion grant; and three clients:

ClientSecretRole
idjag-ac-clientidjagAcSecret1234the requesting app
idjag-ras-clientrasSecret1234redeems the ID-JAG at the resource AS
idjag-introspectintroSecret1234stands in for the API checking tokens

Warning about folder 9

Folder 9 replaces PF's default authentication policy with a simple HTML Form login and turns on IdP authentication policies. That is what makes the real browser login work. It is backed up first (request 0g / 9a) and restored by teardown. Never run it on a PF with production logins. If you skip folder 9, the demo still works through the password-grant shortcut (steps 1.2 and 1.3); only the browser login (step 1.1) needs it.

6. Step 3: run the demo

  1. Import PingFederate-IDJAG-Demo.postman_collection.json.
  2. Postman Settings > General: SSL certificate verification OFF.
  3. Open the collection's Variables tab. Everything is pre-wired for localhost. If your PF is elsewhere change pf_runtime and pf_admin, and set admin_pass (used only by Act 5). The client IDs and secrets already match what the setup created.
  4. Open the Postman Console (View > Show Postman Console) and keep the Visualize tab in view: the tokens are decoded for you.
  5. Run the steps in order, top to bottom.

Say these limits out loud

  • PF is both IdP and resource AS here to keep the demo small; there is no real downstream API (introspection stands in for it).
  • In testing, PF accepted the same ID-JAG twice within its 5-minute life. Do not claim single-use.
  • The ID-JAG here has no client_id claim (the IETF draft and some vendor write-ups describe one).

7. Troubleshooting

SymptomCause and fix
license_agreement_not_accepted from the APIThe license wasn't accepted and the admin password wasn't changed in the console yet (Step 1, point 4).
Setup step 0a fails "needs PingFederate 13.1+"Older PF: no ID-JAG support. Upgrade.
Setup step 0b fails "OAuth role is disabled"Enable the OAuth role in Server Settings > Roles & Protocols (ask the PF owner).
Step 0f "JWKS has no keys" or "HTTP 404"pf_runtime is wrong, or PF's runtime isn't reachable at that URL.
Browser login says "There are no authentication methods available for OAuth"Folder 9 wasn't run (or step 9c, enabling IdP authentication policies, was skipped).
6c or ID-token exchange says "Invalid Token"ID token processor can't verify the signature. The setup embeds PF's JWKS because PF may not trust its own self-signed certificate. If keys rotated, rerun 0f then update processor idjagitp.
Exchange or JWT bearer returns "expired"/"invalid_grant"The ID-JAG lives about 5 minutes. Rerun an Act 2 step, then Act 3.
Introspection returns active: falseThe introspection client needs "validate using all eligible ATMs" (the setup sets it on idjag-introspect).
Setup says "exists, continuing"Safe: an object with that ID already existed. If it was created with a different definition, change prefix or delete it.
Teardown: "adapter / APC / PCV in use"The authentication policy still references them. Run teardown from the top (it restores the policy first).
Postman: SSL errorsTurn off SSL certificate verification in Settings > General.

8. Clean up (optional)

Run folder 11. Teardown in the Setup collection (or ask Claude Code to). It restores the original authentication policy first, then removes everything the setup created. It also deletes the six scopes (openid, profile, email, offline_access, chat.read, chat.history) even if they existed before: skip steps 11u if you want to keep them.

9. Where this goes next

  • A separate resource AS: to show two parties, point a second system at the ID-JAG. Change the SP connection entity ID to that system's issuer, and configure that system to trust this PF's issuer and signing certificate.
  • A real API: add a small service that validates the access token by introspection, so the last step of the flow ("call the API") is real.
  • Real customer IdP login: replace the HTML Form adapter with the customer's authentication policy and point the authorization-code client at it.

Built and tested on PingFederate 13.1.4.
